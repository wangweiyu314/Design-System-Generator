# 02 · 挖掘：从原始取样到 Token 候选

---

## 1. 命令

```bash
$NODE $FACTORY/scripts/mine-tokens.js \
  --online=list.json,form.json,detail.json \
  --figma=figma-vars.json \
  --grid=8 --space-base=4 --min-count=2 \
  --out=mining-report.md \
  --emit-tokens=tokens.draft.md
```

| 参数              | 默认     | 说明                                           |
| :-------------- | :----- | :------------------------------------------- |
| `--online`      | —      | 采集 JSON，逗号分隔多份，会合并统计                         |
| `--figma`       | —      | 设计稿导出，四种形态自动识别                               |
| `--intake`      | —      | 人工标注 JSON（模板见 `examples/intake.sample.json`） |
| `--grid`        | 8      | 期望网格基数，用于标注不合网格的间距；人工标注里填了 `gridBase` 则以它为准  |
| `--space-base`  | 4      | 间距 Token 的档位基数，决定 `--space-N` 的 N 怎么算（见 §3）  |
| `--min-count`   | 2      | 出现次数低于此值不进候选（滤手滑值）                           |
| `--emit-tokens` | —      | 额外产出 tokens.md 草稿表格                          |
| `--json`        | —      | 输出机器可读 JSON                                  |
| `--out`         | stdout | 报告写文件                                        |

**三路数据源至少要有一路。** 优先级与可信度：设计稿导出 ≈ 线上采集 > 人工标注。

### 1.1 人工标注（`--intake`）——兜底路线

Figma 导不出、线上页面又打不开时的第三条路：人照着截图填  
`examples/intake.sample.json`（复制一份改），然后：

```bash
$NODE $FACTORY/scripts/mine-tokens.js --intake=我的标注.json --emit-tokens=tokens.draft.md
```

它不只是「一路数据源」，还能**补齐另两路**：

| 标注里填了                 | 效果                                    |
| :-------------------- | :------------------------------------ |
| `online.collectFiles` | 自动当成 `--online` 用（未显式指定 `--online` 时） |
| `figma.exportFile`    | 自动当成 `--figma` 用（未显式指定 `--figma` 时）   |
| `tokens.gridBase`     | 自动当成 `--grid` 的默认值                    |
| `structure.has*`      | 并入结构特征统计，参与页面类型推断                     |
| `system.pages`        | 作为「人工标注声明的页面类型」列出，无结构信号支撑             |
| `openQuestions`       | 原样列进报告末尾的待确认清单                        |

**代价要说清楚**：人工标注的值没有频次交叉验证——填表人看走眼一处，这里就错一处，  
没有第二路数据能兜住。所以报告里它们单独成节（`附：人工标注取值`），  
草稿里每行也标了 **人工标注** 来源，不要把可信度等同于线上实测。

**字段留空，不要猜。** 空值会被标成未采集，猜的值不会。

## 2. 输出怎么读

### 结构特征 → 该建哪些文档

脚本按类名/标签猜结构（侧边栏 / 顶栏 / 表格 / 表单 / 分页 / 浮层 / 图表 / 卡片 / 标签）。  
猜得不准，但给的&#x662F;**「有没有」**&#x7684;信号，不是精确数量。

判读原则：**信号 > 0 就值得建文档，信号 = 0 就不要建。**  
不存在的页面类型写了文档，只会让人照着做一个系统里根本没有的东西。

**这一节也是 `--type` 类别集的裁决依据。** 建包时 `contract.json` 的 `types` 是**空的**，
`--type` 按 `scripts/templates/` 下的目录名发现——所以「本系统有哪几类页面」
只有两个来源：本节报告 + 本系统的设计稿。报告只认它认识的信号，
设计稿里有而采集没覆盖的类别以设计稿为准。

同理，**浮层契约**（有哪几类浮层）也从本节的弹窗 / 抽屉信号起手，
档位与遮罩类名再去设计稿与线上实现里量。详见产出包 `scripts/templates/README.md`
「怎么裁决本系统的契约」。

### 布局候选 → 该沉淀哪些布局模板

这一节回答的是「本系统实际有几种页面外壳」。聚类**不看类名，看几何指纹**——  
类名千奇百怪（`sider` / `sidebar` / `left-nav` / `aside`），但「侧栏在左边、宽 200、  
高满屏」这件事是客观的，量得出来。

指纹包含：侧栏在哪一侧 / 多宽 / 是否满高 / 是否 fixed，顶栏多高 / 是否通栏，  
有没有面包屑 / 多标签栏 / 收起触发器，导航项数与页签数，主内容区 padding。

同指纹的页面归为一组，一组 = 一套外壳 = 一个布局模板。判读原则：

| 情况            | 怎么做                             |
| :------------ | :------------------------------ |
| 一组里 ≥ 3 个页面   | 基本可以确认是一套真实外壳                   |
| 一组里只有 1–2 个页面 | **样本不足**，报告会明确标注。先补采同类页面，别急着下结论 |
| 所有页面都在同一组     | 本系统只有一套外壳，沉淀一个布局就够              |
| 出现多个组         | 逐套沉淀，生成页面时用 `--layout=<名字>` 指定  |

**这一节是布局沉淀的唯一依据。** 不要凭「中后台一般长这样」补外壳结构——  
采集不到的部分去问设计稿，设计稿也没有的，就是还没有答案。

> 引擎不预置布局，也不认识任何具体系统的类名。沉淀步骤见产出包的  
> `scripts/layout/README.md`，起手文件是 `scripts/layout/_skeleton.html`。

### 颜色候选

每行带 `次数` 与 `用途分布`（background-color / color / border-color）：

- `background-color` 第 1 高频 → 大概率页面底色
- `color` 第 1 高频 → 大概率正文色
- `border-color` 第 1 高频 → 大概率分割线色
- 非灰、用于背景、频次高但不是页面底 → **主色候选**

脚本会给语义初判，但一律标注「必须人工确认」。这个初判基于频次，  
而频次和语义没有必然关系——辅助色可能比主色出现得还多。

### 间距候选与网格拟合

脚本取高频间距的**公约数**作为拟合网格基数：

- 拟合值 = 期望值（如 8）→ 网格规整
- 拟合值 ≠ 期望值 → **别急着改设计**，先确认是不是基线不同（有的系统是 4px 基线）

`不合 Npx 网格` 的清单要逐条看：可能是真的设计不规整，也可能是采集到了图标偏移、边框补偿这类  
本来就不该进 Token 的值。

### 设计稿 ↔ 线上差异

| 差异              | 含义           | 怎么判                     |
| :-------------- | :----------- | :---------------------- |
| **F1 设计稿有、线上无** | 设计稿超前，或设计稿虚胖 | 问设计师：这个变量实际用在哪？说不出来就是虚胖 |
| **F2 线上有、设计稿无** | 线上历史遗留色      | 问：收编进规范，还是线上整改？         |

### 附：人工标注取值

用了 `--intake` 时，报告末尾会多一节「附：人工标注取值」。  
它**故意不占正文章节号**——那是输入的回显，不是分析结果。  
单独成块是因为可信度不同：这些值没有频次交叉验证，  
混进候选表里会被误当成实测结论。

同一节里还会列出 `openQuestions` 里挂起的问题，直接当待办清单用。

草稿（`--emit-tokens`）里，人工标注的值会按类别并进对应小节的表格，  
每行标 **人工标注** 并附原键名。建议的 Token 名只做了  
camelCase → kebab-case 的格式转换，**不是语义判断**——  
转正时务必与本包 `scripts/` 模板里已有的 Token 名对齐。  
| **匹配** | 两边一致 | 最可信的一批，优先定稿 |

**定哪边是意图源，再改另一边。禁止两边各留一个数。**

## 3. 命名规则

不能靠机器裁决语义，但命名格式要统一：

| 类别   | 格式                          | 例                                    |
| :--- | :-------------------------- | :----------------------------------- |
| 颜色   | `--color-<语义>[-<状态>]`       | `--color-primary-hover`              |
| 文本色  | `--color-text-<层级>`         | `--color-text-tertiary`              |
| 功能色  | `--color-<语义>-text` / `-bg` | `--color-error-bg`                   |
| 间距   | `--space-<档位>`              | `--space-4`（档位 4 = 16px）             |
| 字号   | `--font-size-<语义>`          | `--font-size-body`                   |
| 圆角   | `--radius-<档位或组件>`          | `--radius-default` / `--radius-card` |
| 阴影   | `--shadow-<组件/语义>`          | `--shadow-card`                      |
| 组件尺寸 | `--<组件>-<属性>`               | `--floating-header-height`           |

**语义命名优先于视觉命名。** `--color-primary` 而不是 `--color-blue`——  
品牌色从蓝改绿时，前者改一处，后者要全库改名。

### `--space-N` 的 N 是档位，不是 px 值

这是最容易踩的一处：`--space-4` = **16px**，即 `N = px ÷ 4`（4 是间距基数）。  
按 px 值命名会得到 `--space-16` = 16px —— 同一套系统里两个名字指同一个值，  
回灌模板时必然有一边对不上，表现为 `[W1] 规范未收编`。

> 这条规则必须**在沉淀模板之前**定下来：模板 `:root` 里的名字要跟挖掘器的出名字规则对齐，  
> 否则挖掘报告给的是 `--space-4`、模板里写的是 `--space-16`，两边永远对不上。

挖掘器现在按档位出名字（`--space-base` 可调，默认 4）。  
除不尽基数的值（如 6px）会退化成 `--space-6px` 并在报告里标出来——  
那不是命名风格问题，是「它不在本系统的间距阶梯上」，要人工判是设计不规整还是采集噪声。

### 同值不同名不要合并

两个 Token 当前取值相同，不等于可以互换。功能色与涨跌色是典型：  
现在都是红，但功能色会跟着告警语义走，涨跌色跟着境内惯例走，各自演进。  
合并了，将来拆分时才知道有多痛。

## 4. 常见误判

| 现象                | 真因            | 处理                           |
| :---------------- | :------------ | :--------------------------- |
| 大量 `1px` 间距       | 边框宽度被当间距采了    | 看 props 过滤，或提高 `--min-count` |
| 出现十几种灰色           | 同一灰阶被不同透明度渲染  | 按透明度合并，或确认设计稿灰阶档位            |
| 主色候选是灰色           | 页面主色用得少、灰底铺得多 | 从设计稿补，别信频次                   |
| 字号有 `13.5px` 这类碎值 | 浏览器缩放或继承计算    | 忽略，取整数档                      |
| 阴影几十种             | 阴影被多处微调       | 归并成 3–5 档语义阴影                |

## 5. 输出物

- `mining-report.md` —— 给人和 Agent 看的完整报告
- `tokens.draft.md` —— 候选 Token 表格，**草稿，确认后并入 `foundation/tokens.md`**

草稿里的 Token 名是 `--color-candidate-N` 这种占位名，  
必须逐个改成语义名才能转正。占位名进了规范，等于给全库埋了一颗叫 candidate 的雷。
