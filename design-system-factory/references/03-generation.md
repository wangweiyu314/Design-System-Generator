# 03 · 生成：建包与写规范

---

## 1. 建包

```bash
$NODE $FACTORY/scripts/init-package.js \
  --name=<系统名> --prefix=<类名前缀> --out=<目录> \
  [--force] [--no-engine] [--from-mining=<tokens.draft.md>] [--seed-templates=<目录>]
```

| 参数 | 说明 |
| :-- | :-- |
| `--name` | 系统中文名，写入文档与生成器默认系统名 |
| `--prefix` | CSS 类名前缀，小写字母开头，如 `acme` / `tx-bank` |
| `--out` | 默认 `./<prefix>-design-specs` |
| `--force` | 目标目录非空时仍继续 |
| `--from-mining` | 挖掘草稿（`mine-tokens.js --emit-tokens` 的产物），用来预填 `tokens.md` |
| `--seed-templates` | 把一个已有目录下的模板带进 `scripts/templates/`（迁移旧包 / 已有实现补规范） |
| `--keep-values` | 配合 `--seed-templates`：不做取值中性化，保留模板 `:root` 现值 |
| `--no-engine` | 只建文档骨架，不复制引擎（已有实现只想补规范时用） |

### 建包器自动做的事

1. 复制引擎：4 个 JS（`check-tokens` / `check-design-sync` / `install-hooks` / `new-page`）
   + 两份**契约骨架**（`layout/_skeleton.html`、`templates/_skeleton.html`）
   + `templates/contract.json` + 若干说明。**不带任何成品布局与成品模板**
2. **前缀替换**：`gf-` → `<prefix>-`（全库，含 CSS 类名、JS 字符串、注释）
3. **系统名参数化**：`广发中后台系统` → 新系统名；`GF_SKIP_TOKEN_CHECK` → `<PREFIX>_SKIP_TOKEN_CHECK`
4. **路径参数化**：文档里的 `design-specs` → 新包名
5. 生成骨架：`foundation/tokens.md`、`foundation/design-sync.md`、
   `foundation/conventions.json`、包内 `SKILL.md`、`USER-SKILL.md`、四个目录的 README
6. **`tokens.md` 预填**（两路，按优先级）：
   - 有 `--from-mining` → 用草稿的候选值预填（取值来自**本系统**的采集/设计稿，首选）
   - 否则若 `--seed-templates` 带进来的模板有 `:root` → 用它们的 Token 名预填
   - 两路都没有 → 只有表头与填写说明。**这是正常状态**，不是错误
7. 有 `--seed-templates` 时，对带进来的模板做**取值中性化**（除非 `--keep-values`），
   并报告跨模板同名校值不一致

### 建包器不做的事

- 不猜数值 —— 数值只能来自采集与设计稿
- **不预置布局** —— 页面外壳必须按本系统的设计稿/线上实测沉淀（见 §8）
- **不预置内容区模板** —— 「列表页长什么样」的答案同样只在本系统设计稿里（见 §11）
- 不生成组件/页面文档 —— 取决于实际有什么页面
- 不生成标杆页 —— 要先定 Token，再出页面

## 2. 前置：为什么前缀必须换

引擎模板里的类名是 `gf-btn` `gf-table` `gf-modal` 这一套。
如果新包保留 `gf-`，同事看到的是「一个叫 gf 的前缀出现在我们系统里」，
语义错乱，而且将来想改已经扩散到几十个页面了。

**前缀在建包时一次性换掉，成本最低。** 等页面生成完了再换，就是全库搜索替换的灾难。

## 3. 前置：为什么引擎不带成品模板

这条是本工厂最容易「看起来合理、其实是错的」的地方，所以单独说。

直觉上，中后台的表格就是表格、表单就是表单，模板似乎是通用的。**只对一半**：

| 层次 | 是不是通用 |
| :-- | :-- |
| **结构** | 大体相似（卡片式表格、垂直表单、三段式弹窗……） |
| **取值阶梯** | **完全不通用** —— 间距档、色板、圆角档、阴影档全是上一套系统的设计决策 |

模板不只是几段 HTML。它带着一整套 `:root`：`--space-1..16`、`--chart-1..4`、
`--radius-*`、`--shadow-*`……把模板原样搬进新包，等于把这套阶梯也搬了进来。

后果比「数值不对」更麻烦：这些 Token 名会被登记进 `tokens.md`，**每一条看起来都像一个
正经的规范项**，没人知道它从哪来、对应本系统的哪个组件；而校验器是绿的——
因为每个条目都被「登记」了。等到要清理时，已经分不清哪些是真需求、哪些是搬运的副产物。

所以引擎只给**契约骨架**：只声明「模板要满足什么」，不含结构、不含取值。
参考样例（广发的真实模板）放在工厂包 `assets/samples/templates/`，只作参考，不参与建包。

### 那 `--seed-templates` 呢

它存在的意义是**迁移**：你手上已经有一套实现（或旧包），要把它带进新包。
这时模板不是「抄来的」，是「你自己的」，但它们的取值仍需过一遍：

- 默认做**取值中性化**：`:root` 的取值换成 `unset`，只留 Token 名。
  页面渲染出来明显不对（`unset` 不是合法色值），**逼人回灌**，不会静默通过；
  `check-tokens.js` 以 `[E5] 取值待填` 报数，退出码非 0
- `--keep-values` 关掉中性化 —— 仅当模板**本来就是这个系统的**（例如给已有实现补规范）。
  从别的系统派生时用它，等于把别人的取值固化成本系统的规范

> 中性化只解决「取值」这一层。**结构层没有自动化的解法**——
> 迁移进来的模板结构是否适用，只能靠人对着本系统设计稿逐类确认。

### 契约取值同理，而且更容易被当成「通用规律」

同一个道理往上推一层：`scripts/templates/contract.json` 里那几项取值——

- `types`：本系统有哪几类页面
- `overlay.<类别>.sizes`：浮层分几档、每档多宽
- `overlay.<类别>.needles`：注入宿主页时要带走哪些样式规则
- `standalone`：哪些类别不套布局

——都是**某一个系统的设计决策**。但它们看起来特别像「中后台通用规律」：
「弹窗不就是确认 480 / 表单 640 / 复杂 800 三档吗？」不是。
有的系统只有一档确认框，有的遮罩叫别的名字，有的根本没有抽屉。

所以建包时 `contract.json` 是**空契约**（`types: []`、`overlay: {}`），
只保留「字段叫什么、各自管什么」的声明格式说明。
一份填满的样子放 `assets/samples/contract.sample.json`，只作参照。

裁决流程写在包内 `scripts/templates/README.md`「怎么裁决本系统的契约」，
`new-page.js` 在契约为空时会**拒绝执行并打印该走哪一步**——
和「0 个模板报错给沉淀步骤」是同一个模式：不静默用一个默认值糊过去。

> `types` 是**可选**白名单。留空时 `--type` 完全按 `templates/` 下的目录名发现
> （建了什么目录就有什么类别），于是「本系统有哪几类页面」只剩一个来源：设计稿。

## 4. 包结构

```
<prefix>-design-specs/
├── SKILL.md                 # 包内入口：目录结构 / 文档路由 / 强约束
├── USER-SKILL.md            # 用户级入口（精简版），可选装到 ~/.workbuddy-ai/skills/
├── foundation/
│   ├── tokens.md            # 取值唯一来源（预填候选值或 Token 名，人工定稿）
│   ├── design-sync.md       # 设计稿 ↔ 规范映射与同步流程（建包器预置）
│   └── conventions.json     # 本系统的结构级约定（[E4] 逐条校验）
├── components/              # 只写实际存在的组件
├── pages/                   # 只写实际存在的页面类型
├── examples/                # 标杆页
└── scripts/
    ├── check-tokens.js      # Token 双向校验器 + 框架约定回归
    ├── check-design-sync.js # 设计稿 ↔ 规范核对器
    ├── new-page.js          # 页面生成器
    ├── install-hooks.js     # 提交门禁安装器
    ├── README.md            # 脚本索引 + 沉淀与选型
    ├── HOOKS-GUIDE.md       # 门禁说明
    ├── layout/
    │   ├── README.md        # 怎么沉淀本系统的布局
    │   └── _skeleton.html   # 契约骨架（不是布局，`_` 开头不会被生成器选中）
    └── templates/
        ├── README.md        # 怎么沉淀本系统的内容区模板
        ├── contract.json    # 结构性契约：遮罩类名 / 宽度档位 / 提取范围 / --type 清单
        ├── _skeleton.html   # 契约骨架（不是模板）
        └── <类别>/<名字>.html  # 按本系统设计稿沉淀的内容区模板（一开始是空的）
```

> `layout/` 与 `templates/` 的发现规则完全一致：目录里只有契约骨架时，
> 生成器会**报错并打印沉淀步骤**，而不是退化到别的结构。

## 5. 填充顺序（不能乱）

```
① 采集 + 挖掘               拿到取值候选、布局候选、页面类型候选
② foundation/tokens.md      写定稿取值
③ scripts/layout/*.html     按设计稿沉淀本系统的页面外壳
④ scripts/templates/<类别>/ 按设计稿沉淀本系统的内容区模板
⑤ 各模板 :root              回灌取值
⑥ foundation/conventions.json 裁决结构级约定
⑦ components/ pages/        按实际类型写文档
⑧ examples/                 new-page.js 出骨架 + 填真实文案
⑨ SKILL.md                  补文档路由与强约束清单
⑩ check-tokens.js --strict  退出码必须是 0
```

**② → ⑤ 的顺序是硬约束。** 先改模板再补规范，两边就会各留一个数，
而且因为两边都「看起来合理」，往往几个月后才发现。

③ 与 ④ 的先后无所谓，两者互不依赖；但都必须在 ② 之后 ——
模板里的每个取值都应该是「先从 `tokens.md` 查到，再写进去」的。

### 回灌时注意

- 模板 `:root` 只写本模板用到的 Token，不必全量复制
- 缺的 Token 由 `new-page.js` 自动合并（内容区与多标签栏模板的 `:root` 都会被并进去），
  但独立手写的页面要自己补
- 回灌完立刻跑一次校验，别攒到最后；`[E5] 取值待填` 归零才算回灌完成

## 6. 文档骨架

| 场景 | 骨架 |
| :-- | :-- |
| 组件文档 | `assets/doc-skeletons/COMPONENT.md.tpl` |
| 页面文档 | `assets/doc-skeletons/PAGE.md.tpl` |
| Token 汇总 | `assets/doc-skeletons/foundation/tokens.md.tpl` |
| 设计稿映射 | `assets/doc-skeletons/foundation/design-sync.md.tpl` |
| 框架约定 | `assets/doc-skeletons/foundation/conventions.json.tpl` |
| 包内入口 | `assets/doc-skeletons/PACKAGE-SKILL.md.tpl` |
| 用户级入口 | `assets/doc-skeletons/USER-SKILL.md.tpl` |

占位符：`{{SYSTEM}}` `{{PREFIX}}` `{{PREFIX_UP}}` `{{PACKAGE}}` `{{DATE}}` `{{NODE}}` `{{SPEC_ROOT}}` `{{WORKDIR}}` `{{NAME}}` `{{SOURCE}}`

> **骨架只跑占位符替换，不跑前缀/品牌替换规则。** 所以骨架里凡是需要按前缀变形的字面量
> （例如紧急绕过的环境变量名），必须写成 `{{PREFIX_UP}}_SKIP_TOKEN_CHECK` 这种占位符——
> 指望 RULES 去替换它是不生效的。这条踩过一次：新包文档里写的绕过变量名与实际不符。

### 包内入口 vs 用户级入口

| 文件 | 装在哪 | 内容 |
| :-- | :-- | :-- |
| `SKILL.md` | 包根，随包走 | 全量：目录结构 / 文档路由 / 强约束 / 生成参数 |
| `USER-SKILL.md` | 可选复制到 `~/.workbuddy-ai/skills/<prefix>-design-system/SKILL.md` | 精简：只留「怎么找到包 / 怎么生成 / 怎么校验」 |

用户级入口的价值是**跨工作区可用**：不必先 cd 到包目录。
两份都刻意不含任何规范数值，避免双源漂移。

## 7. tokens.md 的表格格式是硬要求

校验器按表格解析本文件来比对交付物：

```
| Token | 默认值 | 用途 |
|-------|--------|------|
| --color-primary | #2A6CDD | 品牌主色 |
```

- 第一列必须是 `--` 开头的 Token 名
- 第二列写 `--` 的占位行**不会被解析**，可以放心做待填骨架；
  ⚠ 但**不要留空** —— 留空会被解析成「这个 Token 的取值是空串」，
  等模板里回灌了真取值就会报「取值漂移」
- 第三列含「预留 / 色板 / 暂不使用 / 不适用 / 保留 / 废弃」→ 识别为预留，不计入「规范未落地」

写错格式不会报错，只会静默漏检——这是最坏的一类失败。

## 8. 布局沉淀：外壳只能来自本系统的设计稿

**引擎不预置布局。** 这不是省事，是刻意的：
布局是「本系统的页面外壳长什么样」的答案，从别的系统抄一套过来，
等于用一个没在本系统验证过的结构冒充答案——而且它看起来是能跑的，
直到有人发现侧栏宽度、面包屑位置、多标签行为全都不对。

### 怎么沉淀

1. **看挖掘报告第 2 节「布局候选」。** `mine-tokens.js` 按几何指纹
   （侧栏在哪一侧/多宽、顶栏多高/是否通栏、有没有面包屑/多标签）把线上页面聚成若干组，
   每组就是一套外壳。样本不足时会明确标注，单页指纹不构成结论。

2. **起手用 `scripts/layout/_skeleton.html`**，不是从别的布局改：

   ```bash
   cp <包>/scripts/layout/_skeleton.html <包>/scripts/layout/<名字>.html
   ```

3. **保留三个插入点标记**（这是与生成器的唯一契约）：

   | 标记 | 必填 | 作用 |
   | :-- | :-- | :-- |
   | `<!-- @content-slot -->` | ✅ | 业务内容插入点。缺了生成器直接报错 |
   | `<!-- @tabs-slot -->` | 选填 | 多标签栏插入点（`--tabs` 用）。没有 = 这套外壳不含多标签栏 |
   | `<!-- @page-title -->` | 选填 | 页面标题文本插入点（`--name` 用） |

4. **类名沿用本包前缀**；取值先登记进 `tokens.md`，再回灌本文件的 `:root`。

5. **校验**：`check-tokens.js <包> --strict` 退出码 0。

### 生成器怎么认布局

`--layout` 的取值 = `scripts/layout/` 下的文件名（不含 `.html`）。

| 情形 | 行为 |
| :-- | :-- |
| 不写 `--layout`，且包内只有一个布局 | 自动用它 |
| 不写 `--layout`，且包内有多个布局 | 报错并列出全部可选值 |
| 不写 `--layout`，且一个布局都没有 | 报错并打印沉淀步骤（见上） |
| `--layout=none` | 只产出内容区，不套外壳（已有项目里加页面时用） |

**一个布局都不做也行** —— 已有项目里加页面本来就不该套外壳。只有「0→1 新建系统」才必须沉淀。

### 布局与内容区是两个层次，但「不能照搬」是同一条规则

| | 布局 | 内容区模板 |
| :-- | :-- | :-- |
| 回答什么 | 本系统的页面**外壳**长什么样 | 本系统某一类**内容结构**长什么样 |
| 怎么发现 | 挖掘报告第 2 节「布局候选」（几何指纹聚类） | 挖掘报告第 1 节「页面结构特征」 |
| 起手文件 | `scripts/layout/_skeleton.html` | `scripts/templates/_skeleton.html` |
| 落位 | `scripts/layout/<名字>.html` | `scripts/templates/<类别>/<名字>.html` |
| 发现规则 | 0 个报错 / 1 个自动用 / 多个要 `--layout` | 0 个报错 / 1 个自动用 / 多个要 `--template` |

这里曾经写过一句「内容区模板跨系统可复用，所以由引擎自带」——
那个判断只看到了结构层，漏了取值阶梯层（见 §3）。
**两者都只能来自本系统设计稿**，区别只在落位与发现方式。

## 9. 框架约定：结构级约束写进 conventions.json

`[E1]/[E2]/[E3]/[E5]/[E6]` 只管**取值对不对**，管不了**结构对不对**。
结构约定（例如「面包屑必须是内容区的首子元素」「页签禁止固定宽度」）写进
`foundation/conventions.json`，由 `[E4]` 逐条校验。

校验器只提供通用断言类型，不认识任何具体系统的类名：

| 类型 | 作用 |
| :-- | :-- |
| `forbid-removed-tokens` | 引用 `tokens.md`「已移除」表里的 Token 即报错 |
| `forbid-property` | 匹配的规则块内禁止出现某属性 |
| `require-property` | 匹配的规则块内必须声明某属性，且值匹配正则 |
| `require-value` | 属性取值必须在白名单内（未声明则不判） |
| `require-value-pattern` | 属性取值必须匹配正则（未声明则不判） |
| `require-rule` | 必须存在「选择器 + 属性匹配正则」的规则 |
| `require-first-child` | 指定子元素必须是容器的首个子元素 |

每条都可加 `when` 前置条件（`hasClass` / `cssHas` / `htmlHas`），
只在「相关元素确实存在」时才生效——组件片段与独立页面会自动跳过，不会误报。

`selector` 怎么匹配由 `match` 决定，三选一：

| 值 | 含义 |
| :-- | :-- |
| `exact`（默认） | 选择器**整体等于**给定值 |
| `contains` | 选择器里**出现**该类，带 `-` / `_` / 词边界（`.x-a` 不命中 `.x-a__b`） |
| `all` | **不筛选择器**，样式表里每条规则都受检（`selector` 可省略） |

`all` 是给**横切约定**用的——「间距一律走 Token」「圆角只允许 N 档」这类约束不针对某个组件，
而针对整张表；靠 `contains` 逐个类名枚举，必然漏掉后来新增的组件。

### 裁决原则

- **只写结构级约定**。凡是能靠 E1/E2/E3/E5 查出来的取值问题，不要写进这里。
- **只写「批量脚本可能漏掉某个文件」的约定**。靠肉眼审结构约定必然漏。
- **不要照抄别的系统的约定**。类名、结构假设都只对那一套系统成立。
  一份真实样例见工厂包 `assets/samples/conventions.sample.json` —— **样例，不要照抄**。
- `rules` 为空不是错。新包在裁决阶段之前本就该是空的，此时 `[E4]` 恒为 0。

### 为什么需要它

批量改造多个布局文件时，靠肉眼审必然漏。例如「面包屑必须是内容区的首子元素」，
漏一个文件就是该页面比别人低一截，而 E1/E2/E3 全 0、校验器报绿。

**结论：框架约定不能只写在文档里 —— 凡是「批量脚本可能漏掉某个文件」的约定，都应进校验器。**

## 10. 标杆页怎么生成

```bash
$NODE <包>/scripts/new-page.js --type=list --name=<真实页面名> --out=examples/demo-list.html
```

**前提**：本包已经沉淀了 `list` 类模板与至少一个布局。
没沉淀时生成器会报错并打印沉淀步骤（`--layout=none` 可只要内容区）——
它不会拿别的系统的结构顶上去。

生成的是骨架 + 规范样式，**业务字段、数据、文案要逐项替换**
（文件里标了 `业务替换点` 注释）。

标杆页的价值：它是「这类页面长什么样」的唯一参考答案，
也是改规范/模板后的回归验证基线。空着不写，规范就只是一堆没有着落的数值。

## 11. 内容区模板沉淀：结构也只能来自本系统的设计稿

**引擎不预置任何内容区模板。** 理由见 §3：模板不只是结构，它还带着一整套取值阶梯。
引擎只给一份契约骨架 `scripts/templates/_skeleton.html` ——
骨架里没有结构、没有取值，只有约束。

### 怎么沉淀第一类模板

1. **先确认本系统确实有这类页面。** 看挖掘报告第 1 节「页面结构特征」
   （`hasTable` / `hasForm` / `hasModal`…）与推断出的页面类型。
   没有仪表盘就不要建 `dashboard/` —— 那等于凭空给系统加了一类页面，
   而它看起来像工厂要求的。

2. **起手用骨架，不是照样例改：**

   ```bash
   mkdir -p <包>/scripts/templates/list
   cp <包>/scripts/templates/_skeleton.html <包>/scripts/templates/list/<名字>.html
   ```

   工厂包 `assets/samples/templates/` 下有广发的 8 类真实模板。
   它们的作用是**回答疑问**（「这类模板一般需要哪些部分」「`:root` 大概要登记什么」），
   不是提供起点。起点是设计稿。

3. **结构照设计稿。** 有哪些区块、什么顺序、怎么排布，全部按设计稿与线上实测来，
   不要凭「中后台的表格一般长这样」补。

4. **取值先登记再回灌。** 用到的尺寸/色值先写进 `foundation/tokens.md`，
   再回灌本文件的 `:root`。反向操作必然产生双源漂移。

5. **类名沿用本包前缀。** 前缀是全库批量替换的锚点，另起一套会让后续替换漏掉这个文件。

6. **标「业务替换点」。** 使用者要改的地方（标题、字段、数据源、提交逻辑）都加
   `<!-- 业务替换点：xxx -->`。缺了它，使用者不知道从哪下手。

7. **标题用占位符。** 页面标题写 `@@页面标题@@`，系统名写 `@@系统名@@`，
   生成时按 `--name` / `--system` 填进去。生成器不认识任何具体系统的类名 ——
   它不会去猜「弹窗标题的 class 叫什么」。

8. **自检**：`node <包>/scripts/check-tokens.js <包> --strict` 退出码 0。

### 浮层的额外一步

弹窗 / 抽屉要能被 `new-page.js` 注入宿主页面，所以除了模板本身，
还要在 `scripts/templates/contract.json` 里声明遮罩类名、宽度档位、
样式提取范围（`needles`）。这份契约是**声明式**的：

- 本系统的弹窗只有两档宽度 → 改 `contract.json`
- 遮罩叫别的名字 → 改 `contract.json`
- 想加一类浮层（比如 `popover`）→ 在 `overlay` 里加一段、建 `templates/popover/` 放模板，
  **生成器不用改**

这和 `foundation/conventions.json` 是同一个思路：
凡是「只对某一个系统成立」的知识，都不该写死在工具里。

**但契约本身是空的**（见 §3）。裁决三件事，全部从本系统的设计稿 / 线上实测来：

| 要裁决什么 | 从哪裁决 |
| :-- | :-- |
| 有哪几类浮层 | 报告第 1 节的弹窗 / 抽屉信号 + 设计稿里实际画的浮层 |
| 每类几档、每档多宽 | 从设计稿量。**档位数不是通用常量** |
| 遮罩类名 / 触发属性 / `needles` | 本系统的类名与属性名；`needles` 从「注入时要带走哪些样式才不残缺」反推 |

裁决完写进 `contract.json`，再建 `templates/<类别>/`，两边类名与档位对齐。
完整流程见包内 `scripts/templates/README.md`「怎么裁决本系统的契约」。

### 反过来同样重要

确实不需要的类别，就别建对应目录。
`new-page.js --type=<类别>` 在该目录为空时会**报错并打印沉淀步骤**，
不会静默产出空页面，也不会退化到别的结构 —— 这是设计出来的行为，不是缺陷。

## 12. 演示区：别让它漏进交付物

为了让浮层骨架看得见、让人能点一下试试，模板与生成器都会造一批**只服务于演示**的 DOM：
触发按钮、假数据、版本说明、「当前激活标签：首页」。

它天生带着「反正是临时的」气质，最容易被免于审查，但它会往两个方向漏，
而且**一条都不报错**：

| 漏向 | 症状 |
| :-- | :-- |
| **注入宿主页** | 别人的页面里凭空多出演示 DOM 与它的样式 |
| **被采集器采到** | 演示区的取值伪装成本系统的设计取值 |

第二条尤其隐蔽。演示区常用 `em` 写相对单位，14px 基准下算出
`7px` / `10.5px` / `3.5px` / `11.9px` / `5.25px`——它们会混进间距与圆角候选。
喂给 `mine-tokens.js` 后，草稿里会长出 `--space-7px`、`--radius-candidate-3 | 7px`
这样的条目；其中 `--space-3 | 12px` **看不出任何异常**，它就是个正经档位名，
只是档位值来自演示条的 `padding: 0 0.75em`。
报告里那句「期望基数 8px → 覆盖偏低」也是被它拖出来的假信号。

### 两个标记，缺一不可

```html
<!-- @transient-start 演示用触发区（业务接入时删除） -->
<div class="demo-launch" data-collect-ignore>
  <button class="你的按钮类名" data-modal-open="modalForm">打开弹窗</button>
</div>
<!-- @transient-end -->
```

| 标记 | 管什么 | 实现 |
| :-- | :-- | :-- |
| `@transient-start/end` | 注入宿主页时整段剔除 | `new-page.js` 的 `stripTransient()`，**按注释切段，不做 HTML 解析** |
| `data-collect-ignore` | 采集时整块跳过 | `collect-from-browser.js` 跳过该元素及其全部后代，并在 `meta.elementsSkipped` 留痕 |

CSS 里的演示区样式用同款标记包在块注释里，`parts()` 会连同 `bodyCss` 一起剔除。

**只在「注入宿主页」时剔除**——独立全屏页（浮层类别、`contract.json` 的 `standalone`
声明的类别、`--layout=none`）不剔除，因为那里演示区往往是页面上唯一能点的东西，
删了就成空白页。
这也正是 `data-collect-ignore` 必须跟着产物走的原因：**独立页最容易被拿去采集**。

### 怎么确认它生效了

采集器会在控制台打印「已跳过 N 个 data-collect-ignore 元素」，
JSON 里也有 `meta.elementsSkipped`。**为 0 而页面上确实有演示区，就是漏了。**

自检 `[S13]` 会把关：样例模板的 `@transient` 标记必须成对，
HTML 段必须带 `data-collect-ignore`，且生成器与采集器两侧的约定名一致。

## 13. 交付路线：什么时候必须加一条「代码路线」

> 本节来自 STARS 包（antd 5）的交付实测：包建好之后发现手写 HTML 到不了
> 「与线上一模一样」，被迫确立双路线。完整的事故与判据见 `04-pitfalls.md` §3.19。

### 判据：目标系统的样式技术栈

| 目标系统 | 路线 | 说明 |
| :-- | :-- | :-- |
| 全局 CSS / Less / CSS 自定义属性 | **单路线**（HTML） | 静态 HTML 能忠实复刻渲染结果，本手册主体讲的就是这条路 |
| CSS-in-JS 组件库（antd 5 等） | **双路线：代码为主、HTML 为辅** | 交互态、图标、字体渲染、动效、滚动条都无法静态复刻——「接近」不是可交付的承诺 |

判据只看一件事：**样式是不是运行时生成的**。是，则静态 HTML 有天花板，
「一模一样」的唯一方式是复用同一套组件库与主题体系写真实代码——渲染引擎相同，效果必然一致。

### 代码路线的产物：包内 `codegen/` 目录

HTML 路线的产物是 `scripts/templates/` + `examples/`；代码路线的产物是 `codegen/`，
四份文档（以 STARS 包为参照，均按本系统实际挖掘结果长出来，**不抄 STARS 的清单**）：

| 文件 | 内容 | 从哪来 |
| :-- | :-- | :-- |
| `README.md` | 权威文件表（页面骨架参照 / 组件统一出口 / 主题 JSON / 路由分支 / 图表色 / 路由注册）+ 标准工作流 + 硬性禁令 | 阶段一源码挖掘（`05-source-mining.md`）+ 阶段四裁决 |
| `page-recipes.md` | 每类页面的代码骨架，**附权威参照文件路径**（参照文件本身是权威，骨架只是导航） | 挖掘报告第 1 节页面结构特征 + 指定标杆页源码 |
| `theme-rules.md` | 主题架构（有无 darkAlgorithm / 逐组件覆盖）、主题 JSON 存放与写法、路由级背景分支、涨跌色与图表色规则 | 源码主题反解 + 裁决 |
| （示例页） | 在**目标仓库里**写一个 demo 页验证路线，README 里记录路由注册与验收状态 | 上述三份文档 |

三条写法纪律（STARS 实测）：

1. **权威文件表里的路径是「仓库相对路径」**，不抄进包里的副本——
   代码路线的单一真值源在**目标仓库**，包只做导航与约束。
2. **硬性禁令逐条写明为什么**（如「tsx 内禁裸色值——主题色走 antd token 或主题 JSON；
   涨跌色常量例外，参照 graph.tsx 模式」）。禁令没写出处，评审时没人知道它是不是随口说的。
3. **禁令的效力范围要裁决**：约束「新页面 + 存量页新增/修改代码」还是全量迁移？
   STARS 裁决为前者（存量不排迁移）——这是用户拍板的设计决策，不是默认值。

### 代码路线的验收闭环

HTML 路线的验收是 `check-tokens.js --strict` 退出码 0；代码路线的验收在**目标仓库的工具链**上：

```bash
cd <目标仓库>
npm run tsc && npm run lint:js         # 类型与 lint 零错误（缺一不算交付）
grep -rn "#[0-9a-fA-F]\{3,8\}\|rgba?(" src/pages/<新页面>/index.tsx
# ↑ 裸色值扫描 = [E1] 在代码路线的对应物（例外项要在禁令里声明）
```

外加路由注册与权限配置说明（页面注册不进去等于没交付）。

> **依赖装不上时**：把「tsc / lint 未跑」**显式写进交付说明**——「待验证」是事实状态，
> 留白会被读成「已验证」。这条是「可见的缺失远好过静默的错误填充」在验收环节的翻版。

### 路线降级后，HTML 模板的定位

加了代码路线之后，`scripts/templates/` 与 `examples/` 的角色从「交付物」变为
**结构走查稿**：用于 PRD 评审阶段沟通结构（区块、档位、间距意图），**不承诺像素一致**。
这个定位要写进包内 `codegen/README.md` 与 `SKILL.md` 的路由表，否则使用者
（以及写走查稿的你自己）会继续拿「像不像」当验收标准，返工无穷。

两条路线**共享同一个 Token 真值源**（`foundation/tokens.md`）：
走查稿的取值来自它，代码路线的禁令（less 主题分支色值必须来自登记表）也锚定它——
路线可以分叉，真值源不能分叉。
