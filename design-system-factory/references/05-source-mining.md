# 05 · 源码挖掘：拿不到设计稿时，前端源码是第三类权威

> 五阶段流程的 ① 采集里，原来只有两条腿：**Figma（意图）** 与 **线上实测（现状）**。
> 这份文档讲第三条腿：**前端源码**。
> 它不是「现状」也不是「意图」，而是**现状的成因**——
> 而且往往带着语义名，这是 computed style 永远给不出的东西。

---

## 1. 什么时候该走这条路

| 情形 | 走源码？ |
| :-- | :-- |
| 拿不到 Figma，只有线上页面 | **必须**。否则规范描述的是「现状」，历史遗留脏值会被洗白成标准 |
| 有 Figma，但线上已严重脱节 | **要**。源码告诉你脱节发生在哪一层 |
| 拿不到 Figma，且线上页面多数无权限 | **必须**。这时源码是唯一能覆盖全站的手段 |
| 有 Figma 且线上一致 | 可以只当交叉验证 |

**用户能提供的东西**（按价值排序）：

1. **前端组件库源码仓库**（最高）——主题配置、组件实现、全局样式都在里面
2. 打包产物（`umi.js` / `main.*.js` 之类）——主题配置被内联在这里，能反解
3. 页面截图 —— 只能验证，不能取值

> ⚠ **别把「要源码」当兜底。** 源码的价值不只是「多一个取值来源」，
> 而是它带 **antd 语义名**（`colorError` / `defaultBg` / `colorBorder`）。
> 频次排序永远推不出「这个红是错误色还是品牌色」，源码一眼就能看出来。

---

## 2. 源码的四个层（按权威度降序）

| 层 | 位置 | 权威度 | 说明 |
| :-- | :-- | :-- | :-- |
| ① 主题配置 | `src/components/<C>/themes/{dark,light,…}.json`、`src/utils/themes/*.json` | **最高** | 每个键是 antd 语义 Token 名，取值即权威 |
| ② 全局样式 | `src/global.less` | 高 | 层级、全局覆盖、跨组件修正都在这 |
| ③ 打包产物内联配置 | `dist/umi.js` 里的 `JSON.parse('{…}')` | 高（与 ① 同源） | ① 在构建时被内联，反解可拿到**全量** |
| ④ 组件源码字面量 | `src/components/**/*.tsx` | **最低** | 散落、易漏、可能互相矛盾——但**只有它能暴露「同一个语义有几套实现」** |

**先扫 ①，扫不全再反解 ③，最后用 ④ 找矛盾。** 反过来（先读组件源码）会被
几十处硬编码淹没，看不出结构。

---

## 3. 怎么把主题配置挖出来

### 3.1 直接读文件（有源码时）

```bash
# 列出所有主题文件，一眼看出有几套主题、覆盖了哪些组件
find src -path '*themes*' -name '*.json' | sort
# 本项目的形状：41 个 light.json + 41 个 dark.json（按组件分目录）
```

`src/utils/themes/normal.json` 这类「无主题后缀」的文件通常是**公共基线**，
两个主题都会 merge 它——别漏。

### 3.2 反解打包产物（没有源码、只有 dist 时）

antd 5 的 CSS-in-JS 主题**不暴露成 CSS 自定义属性**，
所以 `getComputedStyle` 一个都采不到。但 `ConfigProvider` 的 theme 对象是
**以 JSON 字符串内联在产物里**的：

```js
JSON.parse('{"components":{"Tag":{"defaultBg":"#19344E","defaultColor":"#49A0F7","colorBorder":"#1962AC"}}}')
```

提取脚本（Python，跑在 `umi.js` 上）：

```python
import json, re
src = open('dist/umi.js', encoding='utf-8').read()
seen, rows = set(), []
for m in re.finditer(r"JSON\.parse\('(\{.*?\})'\)", src):
    raw = m.group(1)
    if raw in seen:            # 同一段会内联多次
        continue
    seen.add(raw)
    try:
        obj = json.loads(raw)
    except Exception:
        continue
    # 只留像主题的：含 color / fontSize / radius 这类键
    if not re.search(r'color|fontSize|radius', raw, re.I):
        continue
    rows.append(obj)
```

本项目产出：**108 段去重主题 JSON、564 个语义 Token 名**。
这比 computed style 频次统计可靠得多——每一项都自带语义名。

> ★ **判据：有语义名就用语义名，别用「谁出现得多」。**
> 频次只能给出「候选」，语义名直接给出「这是什么」。
> 两者都用时，语义名优先，频次只用来排序「哪些更常用」。

### 3.3 布局常量与条件分支

主题 JSON 里除了颜色，往往还有**布局常量**（顶栏高、侧栏宽、圆角档）。
更隐蔽的是**按路由分流**的函数：

```ts
// src/utils/getTheme.ts
export const getPageTheme = (pathname: string) => {
  if (/^\/risk\/risk-indicator-approval/.test(pathname)) return '#171C26';
  if (['/403', '/credit-trader-workbench', …].some(p => pathname.startsWith(p))) return '#1A202E';
  return '#000000';
};
```

**只打开一页会得出「全站一个底色」的错误结论。** 这类函数必须**整张表**抄进规范，
并且**逐条列出**（不要写成「部分页面用 X」——「部分」不可校验）。

> ⚠ **两张表不一定对称。** 本项目暗色的路由表有 `/403`、`/message` 等 6 条亮色没有，
> 亮色的路由表有 `/user-management` 等 3 条暗色没有。
> 抄的时候**分别抄**，别假设一张是另一张的子集——这本身就是一条待确认项。

## 4. 六个陷阱（都实测踩过）

### 4.1 ★★ 别假设有 `darkAlgorithm`

这是本条路线上**代价最大**的一个假设。很多 antd 项目用
`theme.darkAlgorithm` 换肤，于是「亮色 = 暗色的算法反转」。但本项目：

```tsx
// app.tsx
<ConfigProvider theme={themeConfig}>
// themeConfig = getTheme(themes, themeName, themeConfig)
// getTheme 只做 lodash merge，没有任何 algorithm
```

**暗色 = antd 默认（亮色）算法 + 逐组件覆盖。** 两个后果：

1. **没被主题 JSON 覆盖的 Token，两个主题原生同值。** 不能假定「暗色有的亮色也有」——
   恰恰相反，**没覆盖的就是同值**。
2. **没被包进 `ConfigProvider` 的 antd 组件不响应主题切换**（`message` / `notification`
   挂在 React 树之外，要单独包）。这条要写进包内 `SKILL.md` 的强约束清单。

**判据**：读 `getTheme` 与 `app.tsx` 的实现。
**不要从「项目支持换肤」推断出「用了 darkAlgorithm」。**

### 4.2 ★★ `:root` 与主题覆盖块是一对

有的项目把「主视角」写 `:root`、另一主题另起块；有的反过来。
**生成器 / 注入器 / 校验器三处都必须成对处理**——
只搬 `:root` 会让内容模板带进来的 Token 在另一主题下**静默沿用**当前主题取值。
症状是「页面看着能切主题，实际一半元素没变」。
详见 `04-pitfalls.md` §3.14。

### 4.3 ★ 注释与代码可能矛盾

实测案例：涨跌色的注释写「涨绿跌红」，代码是 `#FF4E4E`（红）/ `#2CAA41`（绿）。

**判据：以代码为准，把矛盾原样记进待确认清单。**
不要默默按注释改——注释可能是过期的，也可能是写反了，
而**这个矛盾本身是给用户的信息**（说明这处历史上改过方向）。

### 4.4 ★ 同一个语义在源码里可能有 N 套实现

实测案例：图表辅助色在 `Line/index.tsx` 里一套
（label 亮色 `#67696E`），在 `ChartCard/LineCard/index.tsx` 里另一套
（label 亮色 `#1a1a1a`）。

**判据：全部列出，标「两套」进待确认，不要挑一套当权威。**
挑一套等于替用户做了一个他没授权的决定，而且另一套还在线上跑着。

### 4.5 ★ `<canvas>` 上的东西采不到 —— 这是能力边界，不是漏采

图表用 ECharts，画在 `<canvas>` 上 → **配色不进 computed style**。

**必须在报告里显式写「不可采」**，否则下游会以为「漏了」，
进而按容器颜色去推断图表配色，编出一套不存在的色板。

**判据（判断到底有没有图表）**：看打包产物，不看 DOM 结构。

```bash
grep -o 'echarts\|antv\|highcharts' dist/*.js | sort | uniq -c
```

> ⚠ 采集器若把 `<svg>` 也算进 `charts` 计数，在图标密集的系统里
> `charts` 数 ≈ 图标数，下游会据此推断出**不存在的仪表盘页**
> （工厂 v1.14 已修，见 `04-pitfalls.md` §3.10）。

### 4.6 ★ 主题切换的过渡会造出「第三套颜色」

用浏览器验证亮色取值时，**必须先关掉 `transition` / `animation`**：

```js
await page.addStyleTag({ content:
  '*, *::before, *::after { transition: none !important; animation: none !important; }' });
await page.evaluate(() => new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r))));
```

否则读到的既不是暗色值也不是亮色值，而是**补间中间值**——
实测读到 `rgb(71,156,245)`，而两端是 `rgb(73,160,247)` 与 `rgb(42,108,221)`。
这类值会伪装成一堆「取值漂移」，把人引向完全不存在的差异。

## 5. 怎么验证源码给的取值

源码给的亮色值必须**能在浏览器里实测复现**，否则不进规范。做法：

1. 页面加载后注入 `data-theme="light"`（或项目实际的切换方式）
2. 关掉过渡与动画（见 §4.6）
3. 量 computed style，与规范逐条比

**判据（三条，缺一条就会出假阳性）**：

- **专属色集合要从「全部颜色 Token」建，不能只从「两主题不同值」的 Token 建。**
  实测：`--color-text-logo` 两主题都是 `#838EA4`，而 `--color-text-tips` 的亮色值也是
  `#838EA4`。只按「亮色 ≠ 暗色」建全集时，`#838EA4` 被算成「亮色专属」，
  于是合法的暗色顶栏字标被报成违规。
- **允许清单要显式列出「另一主题未定义」的 Token。**
  源码里只有 `.rightDark` 没有亮色分支的 Token，切到亮色后**确实**是暗色值——
  这是已裁决的已知项，不该反复报红。
- **反向样例必须真的生效。** 往覆盖块**开头**插一条会被块内后面的声明覆盖 →
  破坏没生效 → 「没报出来」被误读成「这条检查是假绿」。
  反向断言要写成「**每一个**文件都报出」，不是「至少一个」。

## 6. 产出物长什么样

1. **`mining-report.md` 新增一节「源码层取值」**，含：
   - 主题文件清单（几个主题、覆盖了哪些组件）
   - 语义 Token 名 → 取值表（按层：主题配置 / 全局样式 / 组件字面量）
   - 路由条件分支的**完整表**
   - 矛盾清单（注释 vs 代码、多套实现）
   - **不可采清单**（`<canvas>` 等），显式写「能力边界」
2. **`tokens.md` 每行标出处**。本工厂的取值出处只有三种：
   **设计稿 / 线上实测 / 人工确认**。
   源码属于哪一种？**取决于它是不是「意图源」**：
   - 源码里的主题配置是**实现**，不是意图 → 记为「线上实测（源码）」，并在行内注明
   - 用户/设计师看过源码取值后点头 → 升格为「人工确认」
   - 若源码与设计稿冲突 → **记进待确认**，不要自动选一个
3. **待确认清单**。源码挖掘几乎必然产出比线上实测更多的待确认项——
   因为你能看见更多的「不一致」。**这是好事**，说明覆盖面到了；
   把清单交给用户逐条裁决，别自己拍板。

---

## 7. 一句话总结

> **computed style 告诉你「现在画出来是什么颜色」，
> 源码告诉你「这个颜色叫什么、为什么是这个、以及在哪些条件下会变」。**
> 前者是快照，后者是规则。规范要写规则。
