# 04 · 建包会踩的坑

以下每一条都来自真实事故，不是理论推测。

---

## 1. 取值漂移类

### 1.1 单向校验不算数

只查「交付物有没有按规范写」，会漏掉「规范没收编的私有 Token」。
某项目长到 58 个这样的 Token 才被发现——模板里在用，规范里没有，谁也不知道该听谁的。

**做法**：交付前跑双向校验，退出码必须 0。

### 1.2 先改模板还是先改规范

先改模板 `:root` 再补规范，两边各留一个数，且因为都「看起来合理」，
往往几个月后才发现。

**做法**：一律先改 `tokens.md`，再回灌模板。

### 1.3 删除 Token 的隐藏尾巴

删 Token 前要全库扫 `var(--xxx)` 确认零引用。但**「只定义不使用」的页面最容易被漏**——
它们在 `:root` 里声明了却从不 `var()`，规范一删，它们反而变成「规范未收编」。

**做法**：删前三步——①扫 `var()` 引用 ②特别排查只定义不使用的页面 ③留「已移除 → 改用」映射表。

### 1.4 映射表里的替代 Token 要验证存在

写迁移映射时凭记忆写替代 Token，结果那个 Token 根本不存在，
照着改的人会写出一个引用失效的样式。

**做法**：映射表里每个替代 Token 先 grep 验证真实存在。

## 2. 采集与挖掘类

### 2.1 单页采集噪声极大

一个列表页采出来的「主色」很可能是表格斑马纹。

**做法**：至少 3 个不同页面合并统计。

### 2.2 状态色采不到

computed style 只反映当前状态，hover / active / disabled 一个都拿不到。

**做法**：手动触发状态后再采一次，或从设计稿补。

### 2.3 透明度被丢掉

设计稿导出常把填充色与不透明度分开（`#000000` + `60%`），
同步到规范时落成 `#000000` 是最高频的偏差。

**做法**：核对时专门看透明色，落成不透明纯色一律打回。

### 2.4 色阶缺档自行插值

设计稿色阶没导全，规范里自行补了一个中间色。等下次全量导出时对不上，
而这个假色已经扩散到十几个页面了。

**做法**：缺档禁止插值，必须从设计稿原始导出查。

### 2.5 同值不同名被合并

功能色 `--color-error` 与涨跌色 `--color-up` 当前都是红，于是合并。
后来功能色随告警语义调整，涨跌色要跟境内惯例走，拆不开了。

**做法**：语义不同的 Token 不合并，哪怕当前同值。

## 3. 工程实现类

### 3.1 脚本必须实测，纸面推演查不出 bug

某门禁安装器「看代码觉得没问题」，实测才发现两个真 bug：

- 生成的 hook 里 `ROOT` **引用在前、赋值在后**，链式调用原有 hook 永远静默失效
- `uninstall` 只删 `pre-commit`、把原 hook 留在 `pre-commit.local` 不还原

**做法**：建临时仓库跑全流程（`rm -rf /tmp/x && mkdir && git init` 后拷入再测）。

### 3.2 文档承诺的能力，代码必须做得到

两次踩到「文档写了、代码做不到」：

- 校验器传单个文件直接崩（ENOTDIR），而说明书教了这条命令
- 门禁声称保留原有 hook，实测只删不还原

**做法**：写进 SKILL.md 的命令逐条跑一遍再交付。

### 3.3 CSS 取选择器必须先剥注释

模板习惯在规则前写块注释（`/* ===== 按钮 ===== */\n.gf-btn`），
直接 `split('{')[0]` 会把注释算进选择器，
导致「宿主是否已有该规则」的精确去重全部失效、样式被反复注入。

**做法**：切规则前先 `stripComments`。

### 3.4 浮层样式必须加作用域

浮层模板注入宿主页面时，规则一律加遮罩前缀（`.xxx-modal-mask` / `.xxx-drawer-mask`）。
某项目因两套模板的按钮语义相反（布局里裸 `.gf-btn` 是主按钮，浮层模板里是次按钮），
注入后**全站主按钮集体变白**。

**做法**：注入时递归加前缀（`@media` 内部也要加，`@keyframes` 保留全局原名）。

### 3.5 手写 SVG 图表必须 max-height 兜底

SVG 是带内在宽高比的替换元素，`width:100%; height:auto` 下容器变宽会让高度同比例膨胀。
1:1 的环形图曾被拉成 590×590 并撑爆 grid 行高。

**做法**：固定写 `width:100%; height:auto; max-height:300px; margin:0 auto`。

### 3.6 涨跌色要写到 td 级特异性

写成 `.gf-trend--up`（特异性 0,1,0）会被 `.gf-table tbody td`（0,2,1）吃掉，
表现为「写了红绿、页面全是灰的」，且 CSS 和校验器都不报错，只能肉眼发现。

**做法**：写成 `.xxx-table tbody td.xxx-trend--up`。

### 3.7 校验器扫不到 JS 生成的 SVG 属性

色值经 JS 的 `chartToken()` 读 CSS 变量时，校验器只扫 CSS 声明，
**E1 报 0 不代表代码干净**。

**做法**：图表色值必须经 `chartToken()` 读变量，人工确认。

### 3.8 槽位标记替换被注释骗过（`String.replace` 只换第一个）

布局模板的头部注释会**示范**三个插入点标记的写法（`_skeleton.html` 就是这么写的，
照它搭出来的布局都带着一份），而那些示范同样以 `<!-- @content-slot -->` 的字面量出现，
位置比真插入点更靠前（注释在 `<style>` 里，插入点在 body 里）。

`output.replace(SLOT, x)` 只换第一个匹配 → **内容被注进注释、真插入点原封不动留着**。
同源的第二个症状更隐蔽：`layoutRaw.includes(CONTENT_SLOT)` 这个「必填」校验
也会被注释骗过——布局漏写真插入点时照样通过，然后产出没有内容槽的页面。

**代价**：`[E1]`–`[E6]` / `[W1]` / `[I1]` 全部是绿的，产物行数、退出码都一样。
2026-09-23 实测：修复前后两次生成**都是 512 行、都退出码 0**，
差别只是页签上的页面标题渲染成 0×0 宽。

**做法**：换标记前把 `<style>…</style>` 与 `<script>…</script>` 掩成**等长空白**
（等长才不破坏下标），在剩下的部分里取第一个出现；必填校验走同一个函数。
引擎 v1.10 起已内置（`maskedOutsideBlocks` / `slotIndex` / `replaceSlot` / `putSlot`）。
搭完布局自查：生成后正文里搜 `@content-slot`，应该一处都搜不到。

### 3.9 ★ 校验器完全不检查绘制顺序，而它能吃掉整页内容

`check-tokens.js` 只看颜色与 Token 名。**版式与绘制顺序错得再离谱它也是绿的。**

实测（2026-09-23，STARS 外壳）：页面最底层是 `position: fixed; z-index: 0` 的纯黑全屏层，
内容区若**没有** `position: relative`，它就属于更靠下的绘制步骤 →
被黑底整块盖住，**整页业务内容全黑**。

当时的证据长这样：几何断言 **29/29 全过**，连内容区的 computed 底色
`rgb(26,32,46)` 都是对的——错的只是「它画不出来」。

**做法**：

1. 外壳里凡是 `z-index: 0` 的 `fixed` 全屏层，与之同层的静态兄弟都必须显式定位
   （线上 `.ant-pro-layout-content` 就是 `position: relative`，而 `bg-list` 在它之前）。
2. 版式验收必须包含「渲染出来量几何 + 看截图」，不能只看校验器。
3. 断言要能抓住「看不见」，而不只是「值不对」：
   - 关键文本元素宽度 > 0，且 `textContent` 等于期望值
   - 用 `elementFromPoint` 判最上层元素。探测前把 `pointer-events: none` 的层
     临时改回 `auto`，否则它从命中测试里消失、探测恒过
   - 探测点要避开 fixed 容器压在内容区上的重叠带，否则会误报成「被盖住」

### 3.10 ★ 注释里的标签字面量，会把后半份模板吞成「脚本」

与 §3.8 **同源**：注释里的字面量骗过了「只认第一个匹配」的解析。
这次被认错的是 `<script>` 而不是槽位标记。

模板的头部注释为了讲清「这份模板里哪段是通用实现」，会写出标签的字面量。
`parts()` 用 `html.match(/<script(?![^>]*\bsrc=)[^>]*>([\s\S]*?)<\/script>/i)` 找脚本，
**第一个匹配落在注释里的那个字面量上** → 从注释那一点一路吃到文件末尾真正的 `</script>`，
中间的 `@transient` 演示块、另外两个尺寸档的 mask、`</style></head><body>` 全被当成
「脚本内容」塞进宿主页。

**实测证据（2026-09-23，STARS 浮层注入）**：

| 观测项 | 期望 | 实际（修复前） |
| :-- | :-- | :-- |
| 产物行数 | ~600 | **1798** |
| 退出码 | 0 | **0** |
| `check-tokens.js` | 绿 | **全绿** |
| 注入的 mask 块数 | 1 | **3**（三个尺寸档全在） |
| 宿主页 `</head><body>` 出现次数 | 1 | **2**（第二个在 L1597） |
| `@transient` 演示块 | 不得泄漏 | **泄漏**（`data-modal-open` 出现 3 次） |
| `gf-overlay-demo` 演示条 | 应有 | **没有** |

**代价**：退出码 0、所有校验全绿、产物「看起来更长但更完整」——
比缺东西更难发现，因为多出来的内容语法上都合法。

**这次是靠什么抓到的**：浮层验收脚本里有两条**结构性断言**——
「注入的 mask 块必须恰好一个」和「`@transient` 演示块不得出现在宿主页」。
值型断言（颜色、尺寸）全过，只有这两条挂了。

**做法**：

1. 找 `<style>` / `<script>` 之前，先把 HTML 注释掩成**等长空白**，
   在掩过的副本上定位、再按**下标**去原串上切：

   ```js
   function maskHtmlComments(html) {
     return html.replace(/<!--[\s\S]*?-->/g, (m) => ' '.repeat(m.length));
   }
   ```

   等长是关键——掩完下标不变，才能拿掩本的下标去原串切片。
2. 同理，「把 body 内联脚本摘掉」也要走「在掩本上找 `<script>…</script>` 区间、
   再按区间从原串里剪」的路子，否则**注释会被一起剪掉**。
3. 模板里凡是提到标签，注释里**不要写出完整的开标签字面量**；
   非写不可就拆开写（`<` + `script`）。引擎 v1.11 起已内置修复，
   但注释里少一个可能被误认的字面量，永远比多一个安全。
4. 浮层/布局类模板的验收脚本**必须有结构性断言**（块数、标记数、演示块是否泄漏），
   不能只有值型断言。

工厂自检 `[S18]` 用一份「注释里有 `<script>` 字面量 + body 里有真脚本」的
对抗样本守住这条：断言脚本数为 1 且内容正确、body 内联保留注释、
`maskHtmlComments` 掩后长度不变、`<script` 出现次数 2 → 1。

### 3.11 ★ 「图表」被数成了「图标」，于是凭空长出一个页面类型

采集器原先把 `<svg>` 与 `<canvas>` 一起计入 `structure.charts`：

```js
if (tag === 'svg' || tag === 'canvas' || looksLike(el, /chart|echarts|graph/i)) structure.charts++;
```

在图标密集的系统里（antd 的每个图标都是 `<svg>`），这个数≈**图标数**。
而 `mine-tokens.js` 用 `has('charts')` 推断页面类型：

```js
if (has('charts')) pageTypes.push('dashboard（仪表盘页：检测到图表）');
```

**后果链**：没有图表的系统 → `charts` 报出几十上百 →
报告第 1 节写下「dashboard（仪表盘页：检测到图表）」→
被人当成事实写进模板契约的说明里 → 后续照这个说明去建一个不存在的类别。
**每一步都没有任何检查项会报**，因为它不是「算错」，是「口径宽了一档」。

**怎么发现的**：给一个真实的系统写 dashboard 文档时，采到的 6 页 `charts` 报 20–121，
但**没有一页的采集数据里出现图表容器**（连 `.chartWrap` 都是 0 命中）。
顺着数字回到采集器源码，才看见 `tag === 'svg'` 这一项。

**做法**：

1. `<svg>` 单列 `structure.svgIcons`——信息不丢，但不再冒充图表；
   `charts` 只认 `<canvas>` 与带图表语义的类名。
2. **判断「到底有没有图表」不要看采集计数**，去看打包产物里有没有图表库：
   `grep -o 'echarts\|antv\|highcharts\|chart\.js' dist/**/*.js`。
   计数是启发式，打包产物是事实。
3. ★ **图表画在 `<canvas>` 上，配色永远不进 computed style**——这是能力边界。
   坐标轴、网格线、系列色整层都读不到，表现为「图表系列色为空，其余一切正常」。
   图表**容器**（面板 / 工具栏 / 侧栏）是普通 DOM，采得到，**必须收**；
   系列色去设计稿或图表库配置里找，别等采集。

> 同族的坑：`structure.header` 也是类名启发式，在组件库页面里会数到几十个
> （antd 的 `ant-table-thead`、卡片头部……）。**这些数字只用于「有没有」的初筛，
> 不用于计数，也不该被写进给人看的结论里。**

### 3.12 浏览器端注入脚本怎么测 —— 抽成具名函数 + 合成页面

`collect-from-browser.js` 是**注入到别人页面里跑**的脚本，这让它特别难测：
没有模块导出、没有 CLI、跑起来还会触发下载。于是它长期只有 `node --check` 这一层保护，
**口径判错时谁也发现不了**（§3.11 就是这么漏过去的）。

两条做法，配合起来才够：

**① 把要断言的判定抽成不依赖 DOM 的具名函数。**
`isHiddenBox(cs, rect)` 与 `bumpStructure(structure, el, tag)` 都是为此存在的——
`[S17]` / `[S21]` 用 `indexOf` 从源码里把函数切出来 `new Function` 求值，
喂假对象直接跑。**用 `indexOf` 而不是正则**：正则在源码里要写一长串反斜杠，太容易写错。
切到函数结尾靠「两空格 + 右花括号」；函数体里若有嵌套块，切出来会语法错误 →
检查报红而不是静默放行（fail-safe）。
> 注意依赖关系：`bumpStructure` 调 `looksLike`，两个得**一起抽**再拼成一个闭包，
> 否则求值成功、一调用就 `looksLike is not defined`。

**② 口径类的判定还要在真实 DOM 上跑一遍。**
假对象证明不了「浏览器里真的这么数」。做法（`tools/verify-structure-counter.js` 是现成例子）：

```js
const browser = await chromium.launch({ executablePath: CHROME, headless: true });
const page = await browser.newPage({ viewport: { width: 1440, height: 783 } });
/* ★ 必须在下页面之前打桩：采集器跑完会 a.click() 触发下载，
   headless 下进程可能吐完结果却不退出。 */
await page.addInitScript(() => { HTMLAnchorElement.prototype.click = function () {}; });
await page.setContent(FIXTURE, { waitUntil: 'load' });
await page.evaluate((src) => { (0, eval)(src); }, fs.readFileSync(COLLECTOR, 'utf8'));
const res = await page.evaluate(() => window.__DSF_RESULT__ || null);
```

三个要点：

1. **合成页面的数量写死**（5 个 `<svg>` + 2 个 `<canvas>` + 1 个 `.chartWrap`），
   断言才有确定的期望值。元素必须**可见**——采集器默认跳过隐藏节点（§3.1 的坑）。
2. **下载必须打桩**，否则进程不退出（同族的坑见 README「临时件」一节）。
3. **必须断言「旧行为会失败」**。只断言 `charts === 3` 不够——
   若哪天改回混计而页面元素数恰好对上，就会假绿。加一条
   `charts < svgIcons + canvas 数 + 名字匹配数`（即「小于旧口径」）才咬得住。

> 这两层不重复：具名函数的单元测试跑得快、能在自检里常驻；
> 真实 DOM 的测试慢、要浏览器，但它是**唯一能证明「注入后真的按预期工作」**的证据。
> 一个守回归，一个守事实。

### 3.13 ★ 校验器把方向指反了：按规范做反而报错

**症状**：本系统的样式约定要求同一份样式写两个主题分支——

```css
html[data-theme='dark']  { --stars-color-text: #D7DCE0; }
html[data-theme='light'] { --stars-color-text: #313133; }
```

照做之后 `[E1] 硬编码色值` 报出**亮色块里的每一行**；不写亮色块反而全绿。
**即「按规范做报错、不做才过」——校验器惩罚了正确的交付物。**

**根因**：`[E1]` 的白名单（`declaredColors`）只从 `:root{}` 收集，
`parseRootVars` 也只把 `:root{}` 当定义块。主题覆盖块里的取值
既不是 `:root` 定义、又被当成正文使用 → 一律判成硬编码。
**这是口径问题，不是漏检**：旧实现从没打算支持双主题，
而它的「不支持」表现为**假阳性**，比漏检更糟——漏检只是没查出来，
假阳性是**把正确的写法拦住**，逼使用者绕开规范。

**修法**（引擎 v1.15）：把「定义块」的集合从 `{ :root }` 扩成 `{ :root, [data-theme=…] }`，
主题块从正文剔除（它们是定义不是使用），并新增 `[E6]` 查亮色覆盖完整性。
规范侧用四列表格承载亮色列，判别**不靠表头标记**，靠「该行 ≥3 格且第 2 格是色值」——
表头标记是又一个「要靠人记得写」的约定，而格式本身就能自证。

> **教训一：口径类缺陷会以「假阳性」的形式出现，而假阳性更容易被当成「我写错了」。**
> 看到校验器报错，第一反应通常是去改交付物。但当**规范的写法与校验器的口径不一致**时，
> 该改的是校验器。判据：**把交付物改成「不按规范写」之后报错消失了吗？**
> 消失了，就说明校验器在惩罚规范，不是交付物写错了。

> **教训二：反向验证必须两个方向都做。**
> 只跑「新引擎 → 正确交付物 → 绿」证明不了修好了什么——
> 旧引擎在同一个交付物上也可能是绿的（若这个包根本没用到双主题）。
> 必须补第二条：**把引擎改回旧行为，同一份交付物必须报红**。
> `tools/verify-dual-theme.js` 就是为此常驻的：它在临时目录里现场把
> `parseThemeVars` 换成空 Map、`stripThemeBlocks` 换成恒等函数，
> 再跑同一份 fixture，断言退出码从 0 变 1（实测旧行为报 `E1=2`）。
> **「一次就绿的检查」不是证据，「绿→红」的对照才是。**

> **教训三：破坏脚本自己也会「没匹配上」，而它伪装成「检查通过」。**
> 第一次写反向验证时，破坏脚本要替换 `const KEY = "…"`，
> 而源码里那个字符串**带转义引号**，`replace` 一处都没命中——
> 脚本报「自检通过」，其实它什么都没改。
> **做法**：破坏脚本必须断言替换真的发生了：
> ```js
> const before = src;
> src = src.replace(OLD, NEW);
> if (src === before) { console.error('锚点没匹配上，本测试无效'); process.exitCode = 1; }
> ```
> 同族：`indexOf` 锚点用纯文本会命中注释或目录里的同名串，
> **锚点要带足上下文**（`'>生成与校验命令</h3>'` 而不是裸文本）。

> **教训四：自检必须对异常免疫。**
> 把一个 group 的 `parseObjectLiteral` 改成恒抛，整个自检**在 `[8]` 就死了**，
> 后面 9 组一条都没跑，输出看起来只是「第 8 组有问题」。
> **做法**：每组断言各自包 `try/catch`，异常记为「该组失败」而不是中断整个进程——
> ```js
> function group(label, fn) { try { fn(); } catch (e) { fail(label + ' 抛出异常：' + e.message); } }
> ```
> 否则「一组失败」会伪装成「只有一组失败」，掩盖后面真正的连带损坏。

### 3.14 ★ 「一对东西只搬了一半」——生成器并了 `:root`，没并亮色覆盖

**症状**：`new-page.js` 生成页面后报 `⚠ 校验未通过`，但紧接着打印的逐项计数
（`[E1] 硬编码色值 0` / `[E2] 取值漂移 0` / `[E3] 未定义引用 0` / `[W1] 规范未收编 0`）
**全是 0**。看上去像「校验器坏了」或「校验器太严」。

**真因**：报红的是 `[E6] 亮色覆盖不全`，而生成器**只打印了 E1/E2/E3/W1 四项**，
没打印 E6。所以「有一项红了」这件事在输出里只剩一句「校验未通过」，
数字全 0 与结论自相矛盾。

再往里一层：`mergeRootVars()` 把内容模板的 `:root` 并进布局的 `:root`，
**但亮色覆盖块没有并**。于是内容模板带进来的 Token 在亮色下**静默沿用暗色取值** ——
页面看着「能切主题」，实际一半元素还是暗的。

**为什么会漏**：`:root` 与 `html[data-theme='light']` 是**一对**，
但在代码里它们是两段互不相干的文本。写合并逻辑时眼里只有「`:root` 要并」，
亮色块是后加的，加的时候没人回头改合并器。

**对策**：

1. **合并器改成「成对搬」**：`mergeRootVars(layoutStyle, contentRootCss, contentLightCss)`，
   两个参数同进同出；调用点也必须传满三个（漏传就是漏并）。
   布局层没有亮色块时要**新建**一个，不能静默丢掉（旧模板兼容路径）。
2. **校验器输出必须把「红了的那一项」打出来**。计数为 0 与结论为红并列出现时，
   读的人只会怀疑校验器。任何「汇总 + 逐项」的输出，
   汇总的判定条件与逐项打印的集合必须是同一批。
3. **自检钉住**（`[S24]`）：不只断言「新口径并得进去」，
   还要把亮色分支摘掉（`if (contentLightCss) {` → `if (false) {`），
   断言**旧实现并不进去**。否则旧实现也能过，这条检查等于没写。

> **同族缺陷的判据是同一个**：加了 A 之后，**与 A 成对的那个 B 有没有跟着走**。
> 本工厂里已经出现过好几对：契约 ↔ 骨架、文档 ↔ 实现、清单 ↔ 文件、
> `:root` ↔ 亮色覆盖。凡是在代码里分成两段文本、在语义上必须同进同出的东西，
> 都要问一句：我这次只改了一半吗？
>
> **附带的工具教训**：自检里那套「按括号配平抽函数」的 `sliceFunction`
> 原先只跳过字符串，**不认正则字面量**。给 `parts()` 加了一行
> `/html\[data-theme\s*=\s*['"]?light['"]?\]…/` 之后，配平器把 `['"]?` 里的引号
> 当成字符串起点，一路吃到下一个引号，括号配平失败 → `[S18]` 报「抽不出 parts」。
> 抽不出来时它报的是「请同步更新本检查」，看着像检查过时，实际是**源码里多了一个字面量**。
> 修的是配平器（按「上一个有效字符」判断是否为正则起始），不是被抽的源码 ——
> 否则下一个写正则的人会再踩一次。

## 4. 建包流程类

### 4.1 别抄其它系统的强约束清单

抄来的约束在本系统没验证过，等于没有；更糟的是会让人误以为已经处理过。

**做法**：强约束从本系统采集与评审的结果里长出来。
结构级的那些写进 `foundation/conventions.json` 由 `[E4]` 自动校验——
凡是「批量脚本可能漏掉某个文件」的约定，靠肉眼审必然漏，必须进校验器。
工厂包里的 `assets/samples/conventions.sample.json` 是**样例**，类名与结构假设只对那一套系统成立，不要照抄。

> 文档骨架 `PACKAGE-SKILL.md.tpl` 的 §5「强约束清单」**不预置任何条目**（表体是空的）。
> 曾经预置过一行「交付前跑双向 Token 校验且退出码为 0」——那是引擎级要求，
> 放在「本系统的强约束」里是错位，而且它会让使用者以为清单已经有内容了。
> 详见 §5.9。

### 4.2 别建不存在的页面类型文档

预设一套「列表/表单/详情/仪表盘/登录」全建了，
结果系统里根本没有仪表盘页，同事照着做一个出来。

**做法**：按 `mine-tokens.js` 的结构特征信号建，信号为 0 就不建。
`contract.json` 的 `types` 建包时是**空的**，`--type` 完全按 `templates/` 下的目录名发现——
「本系统有哪几类页面」只有设计稿一个来源。详见 §5.9。

### 4.3 占位 Token 名进了规范

草稿里的 `--color-candidate-1` 忘了改名就转正，
之后全库引用一个叫 candidate 的 Token。

**做法**：草稿转正时逐个改语义名，CI 里加一条「禁止 candidate 前缀」的检查也行。

### 4.4 无 git 仓库时删掉的取值不可恢复

本工作区就没有 git。删 Token 前先确认有版本控制，或者先备份。

**做法**：删之前确认仓库状态；没有版本控制就把映射表写全。

### 4.4b 文档里的示例会被校验器当成真 Token

校验器按 `| --xxx | 值 | 用途 |` 解析 `tokens.md`，按 `var(--xxx)` 扫描所有 md。
文档里为了说明格式写的示例，会被当成真实登记项：
`tokens.md` 里写示例 `--color-primary | #2A6CDD`，这个值就成了规范取值，
等你把真正的主色填进模板，E2 会报「取值漂移」——而规范里根本没打算定义这个色。

**做法**：示例一律用匹配不到的占位名，如 `--color-<语义>`、`var(--<组件>-<属性>)`。
尖括号让正则 `[a-z0-9-]+` 匹配失败，既不污染解析又能看懂。

### 4.4c 待填行写 `--` 还是留空，结果不一样

同一个解析器里，「值列是 `--`」和「值列是空」走的是两条路：

- 写 `--` → 被识别为占位行，**跳过**，不进规范
- 留空 → 被当成「这个 Token 的取值是空串」，**进规范**

留空的后果要等到回灌之后才显形：模板里有了真取值，规范里还是空串，
E2 报「取值漂移」——而人会觉得「我明明还没填，怎么会漂移」。

**做法**：待填骨架一律写 `--`。文档里那句「留空或写 `--` 都不会被解析」是错的。

### 4.5 node 路径会变

托管 node 的版本目录带后缀（`22.22.2-2`），写死 `22.22.2` 会 `no such file`。

**做法**：写文档前 `ls ~/.workbuddy-ai/binaries/node/versions/` 确认实际路径。

### 4.6 Bash grep 在部分环境失效

模式含 `--` 或复杂正则时无输出、exit 1。

**做法**：改用 Grep 工具或 node 脚本。

## 5. 不生搬硬套类

「抄」不只有一种形态。下面这几条都是「看起来在做正确的事，实际把别人系统的答案搬了过来」。

### 5.1 引擎预置布局 —— 最隐蔽的一种抄

引擎里带一套现成布局（比如「通栏顶栏 + 浅色侧边栏」），派生新包时它被原样复制过去，
再按需删掉一点。整套流程顺滑得让人不会怀疑。

问题是：**「页面外壳长什么样」正是最不该跨系统借的东西。**
抄来的外壳看起来是能跑的——直到有人发现侧栏宽度、面包屑位置、多标签行为全都不对，
而那时它已经被复制进几十个页面了。

更隐蔽的是**僵尸模板**：从旧分支继承下来的、本系统早已废弃的布局文件，
留在 `layout/` 里没人用也没人删。某次排查发现安装目录里那份 `dark-side-layout.html`
与另一个工作区**逐字节相同**，而两边的文档都声称它「已删除」。

**做法**：引擎不预置任何具体布局。`layout/` 只放契约骨架 `_skeleton.html` 与说明，
本系统该有几套外壳由采集结果裁决。真布局一份都不带。

### 5.2 取值随模板一起带走，校验器还会报绿

只做前缀替换、不做取值处理，新包就会带着上游系统的真实色值/尺寸上线。
**而校验器全绿**——因为 E2 比的是「模板 vs `tokens.md`」，两边都是上游的值，自然一致。

这类问题不会自己暴露：页面渲染正常、校验通过、评审也看不出，
直到有人问「我们的主色为什么和隔壁系统一样」。

**做法（两道）**：

1. **源头**：引擎不带成品模板，新包建出来时 `scripts/templates/` 是空的 ——
   没有上游取值可抄，也就没有可漂移的东西
2. **兜底**：`--seed-templates` 迁移已有实现时，把带进来的模板 `:root` 取值统一换成 `unset`，
   只留 Token 名。`unset` 不是合法色值，页面会明显不对，逼人回灌；同时
   `check-tokens.js` 用 `[E5] 取值待填` 报数、退出码非 0。
   模板本来就是这个系统的（已有实现补规范）时用 `--keep-values` 关掉中性化

### 5.3 把某系统的类名写死在校验器里

结构级校验（`[E4]`）最初硬编码了 8 条断言，断言的是**某一套系统**的 6 个类名。
换一套系统后只有两种结局：全部失效（等于没校验），或拿别人的约定误报（比没有更糟）。

**做法**：校验器只提供**通用断言类型**（禁属性 / 必属性 / 取值白名单 / 必须存在的规则 /
首子元素 / 已移除 Token 复辟），具体断言由各系统的 `foundation/conventions.json` 声明。
`when` 前置条件保证「相关元素不存在就跳过」，组件片段与独立页面不会误报。

### 5.4 多标签栏的 `:root` 没被合并，被「布局恰好声明了」掩盖

生成器把内容区模板的 `:root` 合并进布局，但漏了多标签栏模板。
在多标签栏自带的 `--tab-height` / `--shadow-subtle` 这类 Token 上，
`var()` 引用会落空、渲染成未定义值。

这个 bug 藏了很久，因为**当时的布局模板恰好把这些 Token 都声明了**。
一旦布局改为按本系统设计稿沉淀（`_skeleton.html` 的 `:root` 是空的），前提消失，问题立刻显形。

**教训**：靠「上游数据恰好完整」掩盖的实现缺陷，会一直等到上游变了才爆。
合并逻辑要按「哪些东西会被注入」来写，不是按「当前数据长什么样」。

### 5.5 SVG 表现属性不支持 `var()`

`<stop stop-color="var(--chart-1)">` 这种写法**不生效**——
表现属性不参与 CSS 自定义属性的替换，浏览器按无效值丢弃，图表会静默变黑。

**做法**：一律写成样式声明 `style="stop-color: var(--chart-1)"` / `style="stroke: var(--chart-1);"`。
`fill` / `stroke` / `stop-color` 都适用。

顺带一提：这类 hex 字面量以前会被「该值在 `:root` 里声明过」豁免掉 E1，
取值中性化后豁免消失，9 处硬编码一次性现形——**豁免规则会掩盖硬编码，别依赖它**。

### 5.6 跨模板同名校值不一致，只有比对时才看得见

不同模板里同一个 Token 可能各写一个值（`200ms ease-in-out` vs `0.2s`、
字体栈一个有 `'DIN Alternate'` 一个没有、阴影一种带空格一种不带）。
平时没人会去逐个比对 9 个模板的 `:root`。

**做法（两道）**：

1. **工厂自检 `[S3]`** 对引擎骨架 + `assets/samples/templates/` 逐模板提取 `:root`，
   按 Token 名归并，不一致直接判失败。
2. **建包器**在 `--seed-templates` 复制后做同样的事，不一致就在建包时列出来。

比对前先归一化空白 / `0px` / 逗号间距 / 前导点小数，
否则 `0 2px 8px rgba(0,0,0,.1)` 与 `0px 2px 8px rgba(0, 0, 0, 0.1)` 会被当成两个值，
全是噪音。**单位差异刻意不归一化**——那往往是真的不一致。

> 引擎现在不带成品模板了，这条检查跟着 `assets/samples/templates/` 走——
> 否则它会变成恒绿的空转（没有对象可查）。**检查项要跟着它管的东西搬家**，
> 这是这一轮改造里最容易漏的一类连带影响。

### 5.7 内容区模板的「跨系统可复用」假设，只在结构层成立

这一条是本工厂**推翻过的结论**，值得单独记。

引擎最初自带 8 类内容区模板，理由写在文档里是这么一句：

> 内容区模板（表格 / 表单 / 描述列表 / 指标卡 / 登录页 / 浮层）是**跨系统可复用**的结构；
> 布局是**本系统特有**的外壳。

这句话**只对了一半**。它看的是结构层，漏了取值阶梯层：

| 层次 | 跨系统通用吗 |
| :-- | :-- |
| 结构 | 大体相似（卡片式表格、垂直表单、三段式弹窗……） |
| 取值阶梯 | **不通用** —— `--space-1..16`、`--chart-1..4`、`--radius-*`、`--shadow-*` 全是上一套系统的设计决策 |

建包时做的「取值中性化」只把**值**抹成了 `unset`，
「**存在第 16 档间距**」这件事原样留了下来，随 Token 名预填进 `tokens.md` ——
长得像正经的规范条目，没人知道它从哪来、对应本系统的哪个组件。

**暴露路径**：一次端到端实测里，`[I1] 规范未落地` 报了 7 个 Token 全库零使用
（`--chart-2`、`--chart-3`…）。当时判断成「演示脚本的副作用」，
后来才看清：**那就是这个设计问题的直接证据** —— 规范里那些 Token 不是本系统的需求，
是模板搬过来的副产物。

**做法**：引擎只给契约骨架（`templates/_skeleton.html` + `contract.json`），
成品模板移到 `assets/samples/templates/` 只作参考。发现规则与布局完全同构：
0 个报错给沉淀步骤、1 个自动用、多个要 `--template` 指定。

> **教训：一个「听起来合理」的论证，如果只覆盖了问题的一个层次，就会长期不被质疑。**
> 遇到「X 是通用的」这类判断，先问一句：**通用的是它的哪一层？**

### 5.8 「临时件」会从两个方向漏出去，而它看起来只是演示代码

为了让浮层骨架看得见、为了让人能点一下试试，模板与生成器都会造一批
**只服务于演示**的 DOM：触发按钮、假数据、版本说明、「当前激活标签：首页」。

这些东西天生带着「反正是临时的」气质，所以最容易被免于审查。
但它在两个方向上都会漏：

| 漏向 | 症状 | 本轮实测到的实例 |
| :-- | :-- | :-- |
| **注入宿主页** | 别人的页面里凭空多出演示 DOM 与它的样式 | tabs 模板把整个 body 包在 `.gf-demo` 里，`--tabs` 注入后宿主页多出「当前激活标签：首页」+ 一段版本说明 + 两个演示按钮（9 处） |
| **被采集器采到** | 演示区的取值伪装成本系统的设计取值 | 演示条用 `em`，14px 基准下算出 `7px` / `10.5px` / `3.5px` / `11.9px` / `5.25px`，全部进了间距与圆角候选 |

第二条尤其隐蔽，因为它**不报错**。实测把一份含演示条取值的采集 JSON
喂给 `mine-tokens.js`，草稿里长出了这些条目：

```
| --space-7px    | 7px    | 待确认：出现 4 次（⚠ 不是 4px 的整数倍…） |
| --space-14px   | 14px   | 待确认：出现 3 次（⚠ 不是 4px 的整数倍…） |
| --space-3.5px  | 3.5px  | 待确认：出现 2 次（⚠ 不是 4px 的整数倍…） |
| --space-3      | 12px   | 待确认：出现 5 次          ← 这个最危险
| --radius-candidate-3 | 7px | 待命名：出现 3 次
| --font-size-candidate-4 | 11.9px | 待命名：出现 2 次
```

`--space-3 | 12px` 混在里面**看不出异常**——它就是个正经档位名，
只是档位值来自演示条的 `padding: 0 0.75em`。
`[I1] 规范未落地` 也帮不上忙：它只报「登记了却没用」，不报「用了但不是你的」。
报告里那句「期望基数 8px → **覆盖偏低**」更是被演示条拖出来的假信号。

**做法**：两件事一起做，缺一不可。

1. **注入路径按注释标记剔除。** 演示区用 `<!-- @transient-start -->` /
   `<!-- @transient-end -->` 圈起来（CSS 用块注释同款标记），
   `new-page.js` 的 `stripTransient()` 按标记切段——
   **不做 HTML 解析**（不数标签、不配对），所以标记写错就是写错，不会静默出错。
   只在「注入宿主页」时剔除；独立全屏页不剔除，否则删完就成空白页。
2. **采集路径按属性跳过。** 演示区根元素加 `data-collect-ignore`，
   `collect-from-browser.js` 建一个忽略集合，跳过该元素及其全部后代，
   并在 `meta.elementsSkipped` 里留痕——**留痕是关键**，否则没人知道有没有生效。

**验证方式**：真实浏览器 A/B 对照（同一页面，一次带属性、一次摘掉）：

| | 跳过元素 | fontSizes | spacings | radii |
| :-- | :-- | :-- | :-- | :-- |
| 带属性 | 3 | 无 `11.9px` | 无 `7px` / `10.5px` / `3.5px` | 空 |
| 摘掉属性 | 0 | 有 `11.9px` | 有 `7px` / `10.5px` / `3.5px` / `14px` | `7px` / `5.25px` |

> **教训：引擎自带的「临时件」也是引擎的一部分。**
> `--overlay` 注入的演示入口条曾引用 5 个上游专有 Token 名，
> 在任何新包里必然报 `[E3]`；改成零 Token 之后，它换了个形式继续漏——
> 这次不漏 Token，漏的是**取值本身**。
> 「不报错」不等于「没污染」，得专门设计一个能看见它的观测点。

### 5.9 「预设的条目」比「预设的结构」更隐蔽 —— 它只是一行字

`[S4]` 已经把成品布局、成品模板、成品契约取值挡在引擎之外了。但这一类漏得更早、更散：
**不是结构，而是「已经替使用者想好的条目」**。

| 位置 | 内容 | 为什么它是别人的答案 |
| :-- | :-- | :-- |
| `tokens.md` 骨架的 `### 待确认清单` | 「主色及其 hover / active / 浅底 / focus ring」「功能色四组」「**涨跌色（金融类中后台必填，境内惯例为涨红跌绿）**」「图表系列色」 | 这是**金融类**色板的待办清单。非金融系统照单全收，就会去找一些本系统根本不存在的颜色 |
| `tokens.md` 骨架的分组注释 | 「品牌主色 → 功能色 → 文本色 → 边框与填充 → 背景 → 语义色」 | 某一套系统的色板分组法 |
| `PACKAGE-SKILL.md` §5「强约束清单」 | 表里预置了一行「交付前跑双向 Token 校验且退出码为 0」 | 注释写着「不抄其它系统的清单」，表里已经有一行；且它是引擎级要求，放在「本系统的强约束」里是错位 |
| 引擎 `scripts/README.md` §2.3 | 浮层强约束 8 条（三段式 / `container` 强制 `padding: 0` / Drawer 默认不出 footer / `max-width: calc(100vw - 48px)` / 禁止 `top: 100px`） | 文件自己写着「这些是广发的」——却随引擎进每一个新包 |
| 引擎 `scripts/README.md` §4 | 验收清单里 7 条系统专属项（分页器双倍间距、固定操作列 `border-collapse`、多标签箭头溢出…） | 同上 |
| `new-page.js` / `contract.json` / 三份 README | `--type` 硬编码 `list / form / detail / dashboard / login / modal / drawer` | 「中后台就该有这七类」的暗示；实际类别由目录名裁决，这串名单既冗余又诱导照抄 |
| `contract.json` | `overlay` 的档位与宽度（确认 480 / 表单 640 / 复杂 800） | 真数值，不是占位符 |

**为什么这一类更难发现**：结构层的东西是**文件**，`[S4]` 一眼看得见；
而条目是**文档里的一行字**——它不会让校验器变红，只会让人照着填。
而且「待确认清单」「强约束清单」「验收清单」这些**名字本身就在暗示它该有内容**，
空着反而像没做完。

**做法（三层一起清）**：

1. **条目层**：骨架里的预设条目删掉，换成**指向采集结果**的指针。
   例：`tokens.md` 的「待确认清单」不再列条目，改为指向
   `mine-tokens.js` 报告第 8 节「存疑项」与人工标注的 `openQuestions`——
   那两处产出的是**本系统的**待确认项，而且本来就已经存在，不需要在骨架里再编一份。
2. **类别层**：`--type` 白名单从「必填」改为「可选」。
   `contract.json` 的 `types` 留空 = 完全按 `templates/` 下的目录名发现
   （建了什么目录就有什么类别）。于是「本系统有哪几类页面」只剩一个来源：本系统的设计稿。
3. **契约取值层**：`contract.json` 建包时是**空契约**（`types: []`、`overlay: {}`）。
   一份填满的样子搬到 `assets/samples/contract.sample.json`，只作参照。
   `new-page.js` 在契约为空时**拒绝执行并打印裁决步骤**——
   和「0 个模板报错给沉淀步骤」是同一个模式：**不静默用一个默认值糊过去**。

**连带项（最容易漏的那类）**：`[S4]` 原来的断言是「`contract.json` 必须有 `types` 且非空」。
清空契约之后，这条断言反过来成了「必须带着别人的取值」的推手。
改成**反向断言**——一旦被填上取值就报错。负向测试（临时填回 7 类 + 一档 modal）
确认四条断言全部触发；还原后通过。

> **教训：`[S4]` 挡得住「文件」，挡不住「一行字」。**
> 「引擎不预置成品」这条原则立起来之后，很容易以为已经管住了——
> 实际上漏的是文档骨架里那些**看起来像填写提示、其实已经是答案**的条目。
> 判断标准只有一条：**这条内容，是从采集源长出来的，还是替使用者想好的？**

### 5.10 断言引擎自己的匹配边界 —— `\b` 挡不住 `-`

`[E4]` 有两条选择器匹配路径：`match=exact`（`rulesFor`，整条相等）与
`match=contains`（`rulesLike`，选择器里包含某个类）。`contains` 的边界原本写成 `\b`，
注释还特意解释了它为什么够用：

```js
/* `.x-breadcrumb` 后接 \b 保证不匹配 `.x-breadcrumb__item`
 *（`__` 的 `_` 是词字符，`\b` 不成立） */
```

**这段注释是对的，但只对了一半。** `\b` 确实挡住了 `__`（下划线是词字符），
**却挡不住 `-`**（连字符不是词字符）——而 BEM 的修饰符 `--` 和
「块名是另一个块名前缀」这两种写法，用的都是 `-`：

```
contains: '.x-modal'   →  正则 /\.x-modal\b/
  ✗ .x-modal-mask .x-field__control     ← `.x-modal` 后接 `-`，\b 成立 → 命中
  ✗ .x-modal--base                      ← 同上
  ✓ .x-modal__head                      ← `_` 是词字符，\b 不成立 → 不命中
```

**实际后果是假阳性**：一条「弹窗本体方角无投影」的 `forbid-property` 约定，
把浮层注入后产生的**后代规则**（`.x-modal-mask .x-field__control` 的 `border-radius`）
也判成了违规——等于让人去改本来正确的模板。

**为什么这条特别难发现**：它**只在 `--overlay` 注入路径下才出现**。
直接校验模板是绿的，因为作用域前缀 `.x-modal-mask ` 是注入时才加上去的；
模板里根本没有 `.x-modal-mask .x-field__control` 这样的选择器。
是生成「列表页 + 浮层注入」的示例页时，`[E4]` 才报出来。

**做法**：边界改成负向先行断言 `(?![-\w])`，即后接 `-` / `_` / 词字符都不算命中。
并加 `[S16]` 把边界钉住——抠出 `rulesLike` 喂 8 组样例
（3 组必须命中、5 组必须不命中），负向测试确认改回 `\b` 会红。

> **教训：断言引擎本身也要有断言。**
> `[S15]` 是「解析器读错合法输入」，`[S16]` 是「匹配器判错合法选择器」——
> 两者都是**引擎的缺陷**，不是某个系统的配置问题，
> 症状都不是「不报错」而是**报错报错了地方**（假阳性），
> 而假阳性会让人去改正确的东西，比漏报更贵。
> 凡是「引擎替使用者做判断」的地方，都要问一句：**这个判断的边界，我测过吗？**

### 5.11 模板的「自足性」—— 套了布局跑一遍证明不了模板是对的

内容区模板**可以被独立产出**：浮层类别（`contract.json` 的 `overlay` 里声明的）
与 `--layout=none` 都不套布局外壳，直接输出模板本身。

于是模板里凡是「依赖宿主提供」的东西，都会在独立产出时暴露。最典型的是
**基础重置**——`box-sizing: border-box` 通常写在布局外壳里，
模板自己没写，独立产出时就按 `content-box` 算：

| 部件 | 设计稿 | 独立产出（修前） | 算式 |
| :-- | :-- | :-- | :-- |
| 弹窗标题栏 | 56 | **89** | 56 + 16×2 + 1 |
| 弹窗底栏 | 64 | **97** | 64 + 16×2 + 1 |
| 详情弹窗标签 | 22 | **24** | 22 + 1×2 |

**而校验器全程绿**：`[E1]` 只管颜色字面量、`[E2]` 只比 `:root` 与 `tokens.md`、
`[E3]` 只管未定义引用——**几何算错它们一个都看不见**。
只有把独立产出的页在真实浏览器里量一遍，才会暴露。

**做法**：每个内容区模板自带 `* { box-sizing: border-box; }`。
注入宿主页时这条不会被带走——浮层提取只保留「选择器含 needles」的规则，
`*` 不含任何 needle，会被丢掉。所以写成全局 `*` 是安全的。

> **教训：验证要覆盖「产品被使用的每一种方式」。**
> 生成器有两条产出路径（套布局 / 独立产出），只跑一条就等于只验证了一半。
> 这和 §5.8 的「只跑带标记那组，无法区分标记生效了还是本来就没这些值」是同一个道理：
> **对照组不是可选项，是验证的必要条件。**
>
> 另一条更通用的教训：**「校验器全绿」和「产物正确」是两件事。**
> 校验器只能查它被写成能查的东西。交付前除了跑校验器，
> 还要跑一遍**几何回归**——把产物在真实浏览器里量出来，和设计稿逐项对。
> ZJPT 包交付前共抓到 5 处真实缺陷，其中 3 处是几何量出来的（另 2 处是解析器与匹配器）。

### 3.15 ★ 包交付的三类静默错误（写死绝对路径 / 产物漏搬 / 口径过宽）

这一节来自一次**真正的交付**：把一个已经「跑得通」的设计系统包整理成能发给同事的文件夹。
跑得通不等于交得出去——三类问题都是**交付才暴露**，而且输出一切正常。

#### ① 写死绝对路径 → 校验的是**另一份包**（最严重）

包内 16 个 `tools/*.js` 写死了 `/Users/<某人>/Documents/stars-design-system`。

**关键在那个目录确实存在**（一份旧副本）。于是从新包里跑
`node tools/verify-layout.js`，断言 30/30 全过、退出码 0——
**但它校验的是旧那份包。**

> **写死绝对路径的后果不是「别人跑不了」**（那还算好的，至少会报错），
> 而是**「跑的是另一份包」**。假通过比报错难查，因为输出里没有任何异常信号。

**对策**：
- 产物脚本一律 `path.join(__dirname, '..')` 自定位，**不依赖调用者的 cwd**；
- 机械改写器要**排除自身**——它正文里就写着待替换的路径，第一版把自己改坏了；
- 交付前扫一遍 `grep -rl "/Users/\|C:\\\\" <包目录>`，剩下的应该只有**出处记录**；
- **最终验收在交付副本上跑，最好解压到临时目录再跑一遍**：
  「源目录能跑」不等于「拷出去能跑」。

**根因在生成器**：`init-package.js` 原先往文档骨架里注
`SPEC_ROOT` / `WORKDIR` / `NODE` **三个绝对路径**，于是每个新包一出生就不可移植。
已改：骨架写「本包所在目录（即本文件 `SKILL.md` 的上一级）」+「`which node`」，
具体路径只留在**控制台提示**里（那里给出可复制的路径是有用的）。`[S26]` 守着这条。

#### ② 产物做出来了，忘了搬进包里

两处：`_skeleton.html` 让使用者跑 `tools/inject-light-theme.cjs`，而那个脚本只在**包外**；
`foundation/tokens.md` 说「亮色取值来自 `01-mining/source-theme/`」，
而 `source-theme/` 与 `source-code-findings.md` 也只在包外——
**86 个亮色取值的证据链断在包里。**

这不是笔误，是「产物做出来了，忘了搬进包里」。代价是使用者顺着引用找过去什么都找不到，
而**取值失去了证据**。对策：`check-refs` 这类检查（见 ③）。

#### ③ 检查口径过宽 → 假阳性把真问题埋掉

新写的「文档引用的包内路径是否存在」检查，第一版口径是「反引号里像路径的串」，
**275 条命中**，绝大多数是假的：

- 裸文件名（`button.md`）——它存在，只是带目录前缀，靠文件名无法判定指向哪个；
- 指向**外部仓库**的路径（`Tag/themes/dark.ts` 指 stars-frontend 源码）；
- 指向**别的工具包**的路径（`assets/samples/…` 是工厂的目录）。

**假阳性的代价不是「多几行输出」，是真的那几条会被埋掉**——275 条里夹着 2 条真的，没人会翻。

**收窄到三条判据**：
1. 必须以**本包自己的顶层目录**开头（这类引用才是「对包内有什么」的承诺）；
2. 排除外部仓库的形状——含**首字母大写目录段**的（`components/Button/…`）；
3. **包内没有的后缀**（`.ts` / `.tsx`）一律视为包外。用形状判据，不手列白名单。

剩 7 条：2 条真、3 条外部源码路径、2 条文档**刻意声明「不存在」**的目录
（「这个目录不存在，不是空目录」）→ 这 2 条进显式 ALLOW 并写明原因。

> **宁可留一份短名单，也不要放宽口径。** 口径一放宽，真问题就淹了。
> 同族：`[S22]` 的亮色列判别、`[S16]` 的选择器边界。
> **凡是引擎替使用者做判断的地方，都要问：边界我测过吗？假阳性会拦住谁？**

#### ④ 交付物要配一个「一键验收」总入口

散着 10 来个校验脚本时，**只跑其中几道是最危险的用法**——每个脚本只守一个维度，
漏跑哪道就漏哪类问题，而且漏跑不留痕。

两条细节：
- **「跳过」必须与「通过」分开显示**。两者长得一样，是最容易骗过自己的一种输出。
  环境缺依赖时标「跳过」并说明原因，交付前提醒补跑。
- **扫描根取产物自身，不取它的上一级**。装到 `~/.workbuddy-ai/skills/` 之后，
  上一级是 `skills/`，会去扫**别的技能包**。

> **共同判据**：这三类都不是「某处写错了」，而是**「两边只有一边搬过去了」**——
> 和 `[S24]`（`:root` 与亮色覆盖）、`[S25]`（工厂与介绍页）同族。
> 加了 A 之后，问一句：**与 A 成对的那个 B，有没有跟着走？**

### 3.16 ★ 文档承诺的能力，与代码真做的对不上（计数与清单）

这是 §3.2 的加强版——§3.2 讲「文档承诺了、代码做不到」；
这一条讲**两边其实都做对了，但被复述的那一份没跟着改**。

#### 症状

包交给同事前的最后一次自查，逐字读 `SKILL.md` 时发现：

```text
退出码必须为 0。七项检查：E1 硬编码色值 / … / E5 取值待填 / W1 规范未收编 / I1 规范未落地。
```

而引擎 `check-tokens.js` 头部早已有 `[E6] 亮色覆盖不全`。

**更刺眼的是**：这句是**刚在工厂骨架里修掉的同一个 bug**——
骨架已改成「八项 + `[E6]`」，而**按旧骨架生成的那个包**没改，
于是它带着错句一路进了交付 zip。

同一族还有第二处：`run-all-checks.cjs` 头部写「本包有 10 道验收」，实际 11 道；
`tools/README.md` 里同一处计数也一样。

#### 为什么会漏

这些计数与清单**分散在四五个文件里，全是纯手工散文**，而且：

- 它们**不参与任何构建**——改错了页面照跑、脚本照绿；
- 它们**不报错**——读者以为没查 `[E6]`，于是不去覆盖亮色；
- 它们**看起来像已经同步了**——因为改代码的人与读文档的人，各自只看到自己那一份。

> **判断「有没有漏」不能靠印象。** 包内那份错句，是在「包能不能整体拷走」
> 那一轮里**偶然翻出来**的，不是被检查抓到的。

#### 怎么守

**① 骨架侧（工厂）：`[S27]`**

`PACKAGE-SKILL.md.tpl` §3 会把校验码与项数复述一遍给新包的使用者看。
这份复述此前没有任何检查覆盖——`[S23]` 守工厂自己的自检项数、
`[S25]` 守介绍网页、`[S26]` 守绝对路径，**三处都不管它**。
`[S27]` 补上：校验码集合双向核对 + 项数声明 + 反向样例。

**② 产物侧（每个包）：`check-doc-codes.cjs` + `verify-doc-codes.js`**

判据三条：

1. **校验码集合双向**：文档讲了引擎没有的 → 承诺做不到；
   引擎有文档没讲的 → 读者以为没查。
2. **项数声明**：`N 项检查` / `N 道验收` 必须等于代码里数出来的。
   ⚠ **中文数字也要认**——文档写的是「八项检查」，只认阿拉伯数字会**静默跳过**，
   检查等于白写。
3. **「一条都没扫到」判为失败**。口径失效时返回「0 条不一致」，
   看起来和真绿一模一样——**没扫到 = 没测**。

**③ 别把计数写进「解释这条检查本身」的句子里**

第一版我在 `run-all-checks.cjs` 里写了「『12 道』这个数别手改……」，
结果**这句话自己被检查抓了**。解释性文字里不要复述计数，
否则每加一道都要改两处——而**要改的句子越多，漏一处越容易**。

#### ★ 破坏脚本自己没匹配上，是最像「检查失效」的假象

反向样例的注入代码也要断言「破坏真的生效」：

```js
const patched = src.replace(/\bE6\b/, 'X9');
if (patched === src) {
  bad.push('反向样例注入失败：找不到 `E6` 可替换（破坏脚本自己没匹配上，等于没测）');
}
```

不写这一步的后果：破坏没生效 → 检查当然不报 → 输出看起来像「检查失效」，
于是你去翻检查的代码——**白跑一轮**。

**另一个坑**：反向样例只在**其他项全绿**时才跑。文档真的坏了（`E6` 已被抹掉）时，
注入也会跟着失败，输出里就多一句「反向样例注入失败」——**误导性的二次信息**，
会让人以为是检查自己出了问题。

#### 同族判据

- `[S23]` 工厂 `SKILL.md` 的自检项数 ↔ 实际项数
- `[S25]` 介绍网页 ↔ 工厂（版本 / 项数 / 日期 / 校验码集合）
- `[S26]` 生成器 ↔ 产物（绝对路径）
- `[S27]` **骨架 ↔ 引擎**（校验码集合 / 项数）
- 包侧 `check-doc-codes.cjs` **文档 ↔ 代码**（校验项 / 道数）

> **凡是一份内容被复述到第二个地方，那第二个地方就得有人守。**
> 复述越像「说明性文字」，越容易漏——因为改代码的人不觉得它需要改。

### 3.17 ★ 往产物里注入代码的两个坑：写对内容、写错位置

**场景**：要往一个已经交付的设计系统包里加一个**组件变体**（比如给按钮补一档 32px 高、
给标签补成功 / 危险 / 中性三档）。本包的模型是「**每个模板 / 示例自带它用到的组件样式**」，
所以一个变体要落到**每一个定义了该组件基类的文件**里——漏一个，同名类在不同产物里含义就不同。

于是写一个**幂等注入器**（`--check` 先报、再写入、可重复跑）。两个坑都在这个工具上。

#### 坑一：缩进 —— 工具自己写错位置，而所有校验器都绿

第一版取缩进写的是：

```js
function indentOf(src, idx) {
  const ls = src.lastIndexOf('\n', idx) + 1;
  return (/^[ \t]*/.exec(src.slice(ls, idx)) || [''])[0];
}
// 调用：const indent = indentOf(src, m.index);
```

`m.index` 来自 `/^[ \t]*\.stars-button\s*\{/m` —— 注意正则里的 **`^[ \t]*` 也属于匹配**，
所以 `m.index` **正好落在行首**。此时 `lastIndexOf('\n', idx)` 往回找到的是 `idx - 1`
（上一行的换行符），`ls === idx`，切出来的前缀是**空串** → 缩进判成 `''`
→ 规则被写到**第 0 列**：

```css
  }                                    ← 基类正常，2 空格缩进
.stars-button--md { height: …; }        ← 变体顶格
```

**为什么这条特别值得记**：文件仍然合法、`check-tokens` 的 E1–E6 全 0、
渲染出来的样子**完全正确**——只有肉眼看文件才看得出来。又一个「校验器全程绿的静默错误」。

**对策两条，缺一不可**：

1. **缩进从匹配文本取，不要回头去数行号**：
   `const indent = /^[ \t]*/.exec(m[0])[0];`
2. **让工具自愈**：把「选择器已存在但缩进不对」的行也归一化一遍。
   这样修 bug 之后**重跑一次就全好了**，不必手改产物、也不必写一次性修复脚本。
   判定「已存在」用**选择器**（`.stars-x--y {`），不要用整行——缩进变了也要认出来。

#### 坑二：只补 CSS，不补 HTML 演示 —— 变体选择器是死的

注入器只往 `<style>` 里加规则，产物里**没有任何 HTML 用它们**。后果：产物里出现
「CSS 引用了、HTML 里不存在」的类名 = **选择器静默失效**。

包侧的 `verify-empty-state.js` [A]（「CSS 里出现的本包类名，HTML 的 `class` 里必须都有」）
一次报出全部三个变体。**修法不是加白名单，而是让参考模板演示自己的变体**——
在模板的 `tbody` 里让**每一档各出现一次**（新增两行示例数据即可），并在模板里注明「别删」。

> ⚠ **豁免生效 ≠ 类名真的活着。** [A] 有两类显式豁免：运行时状态修饰符、以及
> 「随浮层 `needles` 一起注入进来的块」。第二类是按**块名前缀**判的
> （`n.split('__')[0].split('--')[0]`）——所以 `stars-button--md` 会因为
> **`stars-button` 这个块被浮层契约带进了名单**而免检，哪怕当前这个文件根本不是浮层宿主。
> 这类豁免会**意外**放过东西。判断某个类名到底有没有被验证过，要去看它命中的是哪条豁免。

#### 收尾：注入器的最小验收

```bash
node tools/add-xxx-variants.cjs --check   # 先看计划，退出码 1 表示有待更新
node tools/add-xxx-variants.cjs           # 写入
node tools/add-xxx-variants.cjs           # 再跑一次：必须「已最新」+ 退出码 0
```

**「再跑一次」是幂等性的最小证据**，也是唯一能同时验证「自愈逻辑没把文件改坏」的办法。
之后必须**渲染出来看**（量 computed 值 + 截图），因为这类 bug 的判据是「位置」而不是「取值」。


### 3.18 ★ 走查稿的「手写层」三类静默错误：漂移、余量摊派、特异性反杀（v1.20，STARS 包实测）

走查稿（examples/*.html）有两层：**模板生成的结构层**和**人手改的表现层**。
校验器 E1-E6/W1 只看颜色与 Token，这一层的层叠、几何、一致性错误全部绿灯放行。
STARS 包（2026-09-29）一天内连踩三个，都是**渲染出来才看见**的：

#### 变体一：示例页与模板漂移

模板里早就有组件豁免规则（`td > span.stars-tag { display: inline-flex }`，连注释都写着
特异性计算），但两个示例页里**没有这条**——生成后被手改过，或来自旧版模板。
用户看到的 Tag 被拉满整列，而模板生成的页面是好的。
**这类不一致没有任何检查盯着**：示例页不在「必须从模板重新生成」的纪律里。

避免法：
- 示例页一律从模板生成；要改先改模板、再重新生成，**不手改产物 CSS**
- 若必须手改（如标杆页填业务文案），只允许改 `业务替换点` 标记的内容；
  交付前用 `diff <(提取模板CSS) <(提取示例CSS)` 之类的一致性抽查，或至少人工比对一遍 `<style>`

#### 变体二：`table-layout: fixed` + 全列固定宽 → 余量按比例摊派

`.stars-base-table { width: 100%; table-layout: fixed }` 且**每列都写死 `width`**：
容器比列宽总和宽时，CSS 规范把剩余宽度**按比例摊给所有列**——
状态列 120px 被撑到 150px+，而 Tag 只有内容宽，右侧一大片空白。
线上真实形态（截图核实）是：列宽贴内容，**余量由文本列吸收**，总宽超出才横向滚动。
这不是编出来的值错了，是**布局算术错了**——E1-E6 全绿，只有渲染量几何才暴露
（又一例印证「自检全绿 ≠ 产物正确」，见 §8 与 v1.15 的并亮色块教训同一族）。

避免法：
- fixed 布局下**至少留一个弹性列**（通常是标题/名称列，不写 width）吸收余量；
  或让列宽总和与容器宽度匹配、多余走横向滚动
- 交付前把走查稿在**目标视口宽度**下渲染一遍量几何（1440 与 1920 各一次），
  专看「某列是否比设计意图宽」

#### 变体三：宽泛容器选择器的特异性反杀

`td > span { display: block }`（单元格省略号，特异性 0,1,2）会压过
`.stars-tag { display: inline-flex }`（0,1,0）——**不管谁写在后面**。
凡是「容器级宽泛规则 + 组件级收缩类」同处一个表格，都要显式豁免：

```css
.stars-base-table td > span.stars-tag { display: inline-flex; overflow: visible; }
```

模板自带豁免还不够——见变体一，示例页丢了它照样翻车。写新容器规则时先盘点：
**页面里有哪些行内组件类会命中这个选择器？**逐个加豁免并注明特异性算式。

#### 流程教训：开工前先找历史采集与既有包

STARS 包开工时没问「之前做过吗」，结果 40MB 的线上采集资产
（computed styles × 6 页、截图 × 12、裁决清单 55KB）就在旁边目录躺着，
工程从零挖了一遍源码，产出还更弱（源码推不出 40px 页签栏、行悬浮色这些运行时事实）。
**采集阶段（§2）第一步改为**：先问用户/先搜工作目录有无历史采集 JSON、截图、旧规范包——
有的话旧包是起点不是对手，做**差异合并**而不是重做。

### 3.19 ★ 包建好之后才暴露的四类问题：路线天花板、验收空洞、改值同步债、单源锁定（v1.21，STARS 包实测）

§3.18 记的是走查稿**渲染层**的错。这一节记的是更深一层——**包建好、投入使用之后**
才发现的路线问题。它们的共同点：在校验器全绿的前提下，交付目标本身发生了偏移。

#### 问题一：手写 HTML 有天花板——CSS-in-JS 系统永远到不了「一模一样」

STARS（antd 5）的交付目标是「与线上页面像素一致」。包建好后第一张真实业务走查稿
（booking-demo，2354 行）就撞上了边界：antd5 是 CSS-in-JS，**交互态、图标、字体渲染、
动效、滚动条都无法用静态 HTML 复刻**——走查稿只能「接近」，永远不能「一致」。
而「接近」在交付语境里是个会持续产生返工的承诺：每个评审环节都会有人问
「这里为什么和线上不一样」。

**出路不是把 HTML 写得更细，是换路线**：既然要一模一样，就用与前端相同的渲染引擎——
复用同一套组件库与主题体系写真实代码。STARS 包据此新增 `codegen/` 目录
（权威文件表 / 页面骨架 / 主题规则 / 硬性禁令，构成见 `03-generation.md` §13），
HTML 模板降级为**结构走查稿**：只承诺结构（区块、档位、间距意图），不承诺像素。

判据：**目标系统用 CSS-in-JS 组件库（antd5 / CSS Modules runtime 类）时，双路线是必选项，
不是加分项。** 传统全局 CSS 系统单走 HTML 路线仍然成立。

#### 问题二：代码路线没有验收闭环——「写了」不等于「交付了」

路线定了之后立刻踩到第二个坑：按 codegen 规范写了示例页（demo-design-spec），
但 **tsc / lint 一次都没跑过**（目标仓库依赖未装）、路由未注册——
它看起来是一份完成的交付物，实际上是一份**未经验证的代码**。
这违反工厂自己的纪律（「脚本类能力必须实测」），但那条纪律只写了「脚本」，
没覆盖「交付给前端仓库的代码」。

代码路线的验收闭环至少四项，缺一不算交付：

| 项 | 为什么 |
| :-- | :-- |
| `npm run tsc` 零错误 | 类型错误在 HTML 路线里不存在，恰恰是代码路线**新增**的失败面 |
| `npm run lint:js` 零错误 | 同上 |
| 裸色值扫描（tsx 内 `#xxx` / `rgba(`） | 这是 `[E1]` 在代码路线的对应物——校验器管不到仓库代码 |
| 路由注册 + 权限配置说明 | 页面写好了注册不进去，等于没交付；权限体系往往要额外配置 |

> **依赖装不上时怎么办**：把「未跑 tsc/lint」**显式写进交付说明**（README 里单列一节），
> 而不是留白。「待验证」是事实状态，「看起来验证过」是假状态——留白会被读成后者。

顺带记两个代码路线特有的坑（都在 STARS demo 页实测）：
- **非泛型组件**：`BaseSelect` / `BaseTable` 等是 `ForwardRefExoticComponent`，
  不支持 `Select<T>` 写法——类型约束写在 props 上。这类约束必须写进 codegen 的禁令清单。
- **静态方法绕过主题**：`message.info()` 挂在 React 树外，不响应主题——
  必须走包了 Provider 的 hook。这是「源码侧第三条腿」在代码路线的延伸。

#### 问题三：破坏性更正的同步债——裁决改了值，引用不会自己跟上

STARS 裁决把弹窗宽度从 15 个实测值收敛为 6 档，其中两条是**破坏性更正**：
旧 `--form` 720 并入 680、旧 `--wide` 1600 并入 fluid。裁决记录里写着
「引用旧值处需同步」——但**同步是手工的**，而且引用散在文档、模板、示例页、
codegen 四类文件里。同类问题此前已发生（图表系列 3 色 → 30 色时只改了 `tokens.md`，
`pages/dashboard.md` §5.3 的旧结论没人动——§12.2 第 3 条）。

这不是记性问题，是**没有把「改值」和「扫引用」绑定成一个动作**。破坏性更正
（改档位、改语义取值、改归并关系）落地时必须：

1. **全库 grep 旧值**（不只是包内：`codegen/` 的规则文档也要扫），
   列出每一处命中——文档、模板、示例、codegen 四类；
2. 逐处同步为新值，或显式标注「存量迁移项，不强制改」；
3. 归并映射写进裁决记录（旧值 → 新档），后人排查线上旧值时有据可查。

> 「一对东西只搬了一半」的判据第四次生效：v1.16 是 `:root` 与亮色覆盖，
> v1.17 是工厂与介绍页，v1.18 是骨架与包——这一次是**规范值与它的全部引用**。

#### 问题四：语义值的单源锁定——小样本结论会被大样本推翻

涨色（境内）在规范里锁过 `#FF4E4E`（出处：K 线组件源码常量）。
五页标杆页源码挖掘后发现：另一个页面族（转债监控，自绘 ColorfulNumberComp）
用 `#D12B2B`，且两个页面独立实现、跨页一致——**多页证据推翻了单源结论**，
最终改判 `#D12B2B`（旧值降为存量迁移项）。同一轮里，「`#D12B2B` 全库只此一处」
这条**更早的旧结论也被作废**——它是在更小的挖掘范围里得出的。

两条教训：

- **「全库只此一处」必须记录搜索范围**（搜了哪些目录 / 哪些文件类型 / 当时全库多大）。
  范围外出现同值时，旧结论自动失效——但只有记了范围，才知道「范围外」是哪。
- **新增标杆页挖掘后，要复核既有语义结论**。样本扩大是推翻小样本结论的最常见方式；
  挖掘报告不应只产出「新发现」，还应带一张「本轮复核过的既有结论」清单。

#### 流程教训：团队规范库也要在第 0 步找

STARS 包后期整合了团队 AI 规范库（61 篇 `index.md`）：**只索引不复制**
（复制会制造双真值源），另建一份「团队规则 ↔ 本包 Token」的逐条映射
（`team-rules-map.md`）。整合中抓到两个值得记的点：

- **交叉验证的红利**：团队规范要求「自定义颜色必须考虑明暗两套」，与包从源码
  `dark.json`/`light.json` 推断出的双主题，是**两条独立路径走到同一结论**——
  这类吻合本身就是置信度证据。反过来，「应用级没有 darkAlgorithm」与团队规范
  「未封装组件用 darkAlgorithm 补主题」看似矛盾、实则互补（应用级没有、组件级逐处补），
  矛盾点要写清成因而不是二选一。
- **目录名撞车**：包内曾建 `docs/`，而团队库也有 `docs/`——文档里裸写 `docs/skill.md`
  时引用检查把它当包内路径，报出 4 个假「不存在」。**包内目录名要避开外部库的
  引用前缀**；指外部文件一律带仓库名前缀。
