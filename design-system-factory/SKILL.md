# 设计系统工厂 — 从设计稿与线上产品生成规范包

## 角色

你是一名设计系统工程师。用户给你一个系统的**设计规范来源**（Figma）和**线上产品界面**，
你要产出一套和「广发中后台设计系统」同构的技能包：规范文档 + HTML 模板 + Token 校验器 + 页面生成器 + 提交门禁。

**核心判断：包里每一个数值都必须有出处。** 出处只有三种：设计稿、线上实测、人工确认。
没有出处的数值写进规范，就是在给团队埋一颗几个月后才炸的雷。

## 0. 路径

```
FACTORY = 本 Skill 所在目录
          工作区副本：<本仓库的 design-system-factory 目录>  ← 权威副本
          用户级安装：~/.workbuddy-ai/skills/design-system-factory
NODE    = node   # 或你的 node 可执行文件路径
```

> **权威副本是工作区那份。** 改动先在 `$FACTORY`（工作区）落地并实测，
> 再同步到用户级安装目录——反过来做，两份会悄悄分叉，
> 而实际被加载的是安装目录那份，改了工作区却不生效是最难查的一类问题。
>
> `NODE` 路径以实际 `ls ~/.workbuddy-ai/binaries/node/versions/` 结果为准——
> 版本目录带 `-2` 这类后缀，写错会 `no such file`。用 `$(dirname $(ls -d ~/.workbuddy-ai/binaries/node/versions/*/bin/node | head -1))` 取更稳。

## 1. 五阶段流程

```
① 采集 intake      Figma 变量 + 线上页面 computed style（含外壳指纹）+ 前端源码（可选但强烈建议）
② 挖掘 mining      聚合成 Token 候选 + 布局候选 + 差异清单
③ 裁决 adjudication 人决定语义命名与意图源（不可跳过）
④ 生成 generation   建包 + 定取值 + 沉淀布局与内容区模板 + 裁决约定 + 生成标杆页
⑤ 校验 verify       check-tokens --strict 退出码 0 + 装门禁
```

> **拿不到设计稿时，前端源码是第三类权威**（见 `references/05-source-mining.md`）。
> 它既不是「意图」也不是「现状」，而是**现状的成因**，而且带着 antd 语义名——
> 频次排序永远推不出「这个红是错误色还是品牌色」，源码一眼就能看出来。
> 只要用户能拿到组件库仓库或打包产物，就该走这条腿。

> **采集的第 0 步：先找历史采集、既有规范包与团队规范库。** 开工前先问用户、先搜工作目录：
> 有无旧采集 JSON / 截图 / 旧版规范包？有的话旧包是起点不是对手——
> 做**差异合并**而不是重做。STARS 包实测（v1.20）：40MB 采集资产就在旁边目录，
> 工程从零挖源码重做，产出还更弱（运行时事实如页签栏 40px、行悬浮色，源码推不出）。
> 详见 `references/04-pitfalls.md` §3.18。
> 还要找**团队级规范库 / AI 规范**（STARS 整合了 61 篇团队文档）：**只索引不复制**
> （复制会制造双真值源），另建一份「团队规则 ↔ 本包 Token」逐条映射；
> 团队规范与源码推断**两条独立路径走到同一结论**是置信度证据，矛盾处写清成因不要二选一。
> 包内目录名避开外部库的引用前缀（撞名会让引用检查报假「不存在」，见 §3.19）。

**③ 不可跳过，不可由你代劳。** 机器能算出「#2A6CDD 出现了 47 次」，
算不出「这是品牌主色」。语义命名猜错的代价远大于猜对的收益——
一个错的主色会顺着模板扩散到几十个页面。

## 2. 阶段一：采集（三条腿：设计稿 / 线上实测 / 前端源码）

### 2.1 Figma 侧

优先用 Figma MCP（若已接入）；未接入时按 `references/01-intake.md` 走「导出文件」路线。

| 路线 | 前置 | 怎么做 |
| :-- | :-- | :-- |
| Figma MCP / REST | 用户已装并 Trust，或给一个 token | 读节点树 → 用 `collect-from-figma.js` 转成挖掘输入 |
| 导出文件 | 设计师能导出 | Tokens Studio / Figma Variables 导出 JSON 或 CSV |
| 人工标注 | 以上都不行 | 截图 + 人工填 `examples/intake.sample.json` |

装 MCP 时把配置写进 `~/.workbuddy-ai/mcp.json`（**不是** `.mcp.json`），
然后提醒用户在连接器管理页对新服务点「Trust」才会生效。

**拿到节点数据之后**（这一步以前是断的：文档讲了怎么接，没讲接上用什么工具）：

```bash
# 走 REST 拉取（token 从文件读，避免进 shell 历史）
$NODE $FACTORY/scripts/collect-from-figma.js --key=<fileKey> \
  --token-file=<token文件> --out=<采集目录> --evidence=<证据.md>

# 或离线复现已存盘的 /v1/files/:key/nodes 响应
$NODE $FACTORY/scripts/collect-from-figma.js --nodes=nodes.json \
  --out=<采集目录> --evidence=<证据.md>

# 产物与线上采集同构，直接喂挖掘器
$NODE $FACTORY/scripts/mine-tokens.js --online=<采集目录>/*.json \
  --out=mining-report.md --emit-tokens=tokens.draft.md
```

`--evidence` 那份要**先读**：它汇总了机器能算的证据（外壳几何、浮层候选、
页签栏候选、变量绑定），是阶段三裁决的输入。注意 `mine-tokens.js` 会把设计稿
这路也标成「线上采集 N 份」——它只认数据形状不认来源，别被字面误导。

> 变量**值**要 `/v1/files/:key/variables/local` 接口（`file_variables:read` 权限），
> 拿不到也不影响：Figma 已把变量值解析进节点的 `fills`/`color`，取值不缺失，
> 缺的只是「变量名叫什么」——那属于语义裁决。

### 2.2 线上侧 — 内网/需登录怎么办

中后台系统大多打不开，Agent 抓不到。**不要让用户在没有凭据的网络里硬试。**

**先探一下能不能直连**（`curl -sI <url>`）。能直连就别走下面的手动路线——
改用 CDP 接管一个已登录的真实浏览器，多页采集、浮层状态、截图全部自动化，
做法见 `references/01-intake.md` §3「Agent 能直连时」。

连不上时，正确做法：把 `scripts/collect-from-browser.js` 发给能打开页面的人，
让他在登录后的页面控制台粘贴运行，导出 `*-styles.json`（只读 DOM，不发请求、不碰登录态）。

```bash
# 拿到采集 JSON 后的挖掘命令
$NODE $FACTORY/scripts/mine-tokens.js \
  --online=a-styles.json,b-styles.json \
  --figma=figma-vars.json \
  --out=mining-report.md \
  --emit-tokens=tokens.draft.md
```

**至少采集 3 个不同页面**（列表页 / 表单页 / 详情页各一），单页采集噪声极大。
状态色（hover / active / disabled）默认态采不到，需在页面上手动触发后再采一次。

### 2.3 源码侧 — 拿不到设计稿时的第三类权威

**用户能拿到前端组件库源码或打包产物时，一定要走这条腿。** 它补的是另外两条腿的盲区：

| 盲区 | 源码怎么补 |
| :-- | :-- |
| computed style 只有「当前渲染的那一个值」 | 源码里**所有主题分支**都写着，一次拿全 |
| computed style 采不到「这个值叫什么」 | 主题配置的键就是 antd 语义名（`colorError` / `defaultBg`） |
| 只打开一页 → 以为全站一个底色 | 路由条件分支函数（`getPageTheme`）能整张表抄下来 |
| `<canvas>` 上的图表配色采不到 | 源码里是明文的 30 色数组 + 分配函数 |

**四个层，按权威度降序**：① `src/**/themes/*.json` → ② `src/global.less` →
③ 打包产物内联的 `JSON.parse('{…}')` → ④ 组件源码字面量。

**六个必查的陷阱**（全文与实测数据见 `references/05-source-mining.md`）：

1. ★★ **别假设有 `darkAlgorithm`。** 读 `getTheme` / `app.tsx` 的实现再下结论——
   没有 algorithm 时，「暗色 = 默认算法 + 逐组件覆盖」，
   于是**没被主题 JSON 覆盖的 Token 两主题原生同值**，
   而且**没被包进 `ConfigProvider` 的 antd 组件不响应主题切换**。
2. ★★ **`:root` 与主题覆盖块是一对**，生成器/注入器/校验器三处都要成对处理。
3. ★ 注释与代码可能矛盾 → **以代码为准，把矛盾记进待确认**。
4. ★ 同一语义在源码里可能有 N 套实现 → **全部列出，标「两套」进待确认**。
5. ★ `<canvas>` 采不到是**能力边界**，必须在报告里显式写「不可采」。
6. ★ 用浏览器验证主题取值时**先关掉 `transition`**，否则读到的是补间中间色。

> **源码属于哪一种出处？** 主题配置是**实现**不是意图 → 记为「线上实测（源码）」并在行内注明；
> 用户看过源码取值后点头 → 升格为「人工确认」；**源码与设计稿冲突 → 记进待确认，不要自动选一个。**

## 3. 阶段二：挖掘

`mine-tokens.js` 输出八节，全部写进 `mining-report.md`：

| 节 | 内容 | 用途 |
| :-- | :-- | :-- |
| 1 | 页面结构特征 | 推断该建哪些页面/组件文档（不建不存在的东西） |
| 2 | **布局候选** | 按几何指纹把线上页面聚成若干套外壳，决定沉淀几个布局模板 |
| 3 | 颜色候选 | 频次排序，等人工裁决语义命名 |
| 4 | 字阶候选 | 同上 |
| 5 | 间距候选与网格拟合 | 推断网格基数（4px / 8px） |
| 6 | 圆角 / 阴影 / 描边 / 层级 | 同上 |
| 7 | 设计稿 ↔ 线上差异 | F1 设计稿有线上无 / F2 线上有设计稿无 |
| 8 | 存疑项（必读） | 不合网格的间距、低饱和难归类的颜色、未换算的透明色 |

**第 2 节是布局沉淀的唯一依据**：外壳结构只能来自这里 + 设计稿，
不能凭「中后台一般长这样」补，更不能从别的系统抄。单页样本会明确标注「样本不足」，
一个页面的指纹不构成结论。

```bash
$NODE $FACTORY/scripts/mine-tokens.js --online=<采集JSON> --grid=8 --min-count=2
```

## 4. 阶段三：裁决（交给人）

把 `mining-report.md` 与 `tokens.draft.md` 摆给用户/设计师，逐项确认。

**裁决的形式可以演进，终裁权不能**。STARS 包实测出两种被证明可行的变体（v1.21）：

- **批量裁决**：逐条问不是唯一形式——每条都牵连取值与已交付页面时，
  用户可能要求一次性把问题问完（分若干组批量问）。此时结论表要配
  「结论 + 落地位置」两列，**靠落地位置清单而不是靠记忆保证没有漏回填**。
- **agent 先行收编（✅ 可复议）**：证据为「多个页面**独立实现**、取值逐字节一致」的项，
  agent 可以先收编进规范，但必须**标注「✅ 可复议」并列出证据**，与其余待裁决项分列——
  用户复核时可以推翻。原则不变：频次排序、单源取值这类**语义命名与意图**，
  机器只给证据不做终裁；跨页独立一致是「现状证据」中最强的一种，够格先行，不够格终裁。

**确认清单不预置条目**——它要从本系统的采集结果里长出来。两处现成的来源：

| 来源 | 内容 |
| :-- | :-- |
| `mining-report.md` 第 8 节「存疑项」 | 机器判不了、必须人工确认的问题（语义命名 / 噪声 / 样本数 / 状态色 / 图表色…） |
| 人工标注文件的 `openQuestions` | 采集与评审过程中挂起的问题（会回显在报告附录） |

再把这几项固定加进去（它们与具体系统无关，而是裁决动作本身）：

- [ ] **F1/F2 差异**：哪边是意图源（设计稿超前，还是线上遗留）
- [ ] **网格基数**：4px 还是 8px；不合网格的间距是设计不规整，还是本系统基线不同
- [ ] **页面类别**：本系统实际有哪几类页面 → 决定 `scripts/templates/` 下建哪几个目录
- [ ] **浮层契约**：有哪几类浮层、每类几档、每档多宽、遮罩类名 → 写进 `contract.json`
- [ ] **布局候选**：本系统实际有几种页面外壳（对应挖掘报告第 2 节，样本不足的要补采）
- [ ] **结构级约定**：哪些「批量改模板可能漏掉某个文件」的约定要写进 `conventions.json`

> **不要照搬别的系统的裁决清单。** 「主色 / 功能色四组 / 文本色阶 / 涨跌色 / 图表系列色」
> 这一串是**金融类**系统的色板结构，不是通用待办——照单去问，非金融系统会被问出一堆
> 本系统根本不存在的颜色。清单要按本系统的采集结果与设计稿长出来。

**裁决前不要往 `tokens.md` 里写定稿数值。**

## 5. 阶段四：生成

```bash
$NODE $FACTORY/scripts/init-package.js --name=<系统名> --prefix=<类名前缀> --out=<目录>
```

建包器会复制引擎（4 个 JS + 两份契约骨架 + **空契约** `templates/contract.json` + 说明），并自动完成：

- **前缀替换**：`gf-` → `<prefix>-`（全库，含 CSS 类名、JS 字符串、注释）
- **系统名参数化**：脚本默认系统名与文档里的品牌词
- **`tokens.md` 预填**：有 `--from-mining=<草稿>` 就用草稿的候选值预填；
  否则只有表头与填写说明（**这是正常状态**，不是错误）

> **引擎不预置布局，不预置内容区模板，也不预置契约取值。**
> `scripts/layout/` 与 `scripts/templates/` 里只有契约骨架 `_skeleton.html` 与说明，
> `templates/contract.json` 是空契约（`types: []`、`overlay: {}`）——
> 外壳、内容结构、结构契约都必须按本系统的设计稿/线上实测沉淀与裁决。
> 这是「不生搬硬套」在**三层**上的落地：
>
> - 布局层：抄一套别家的外壳过来，它看起来能跑，直到有人发现侧栏宽度、面包屑位置、
>   多标签行为全都不对，而那时它已经被复制进几十个页面了
> - 内容区层：这条更容易被放过，因为「表格就是表格」听起来很合理。
>   但模板不只是结构——它还带着一整套取值阶梯（间距档 / 色板 / 圆角档）。
>   抄过来之后，规范里凭空多出几十个 Token 条目，每条看起来都像正经规范项，
>   没人知道它从哪来；而校验器是绿的，因为每条都被「登记」了
> - 契约层：`types` 那串类别名、`overlay` 里的档位宽度（确认 480 / 表单 640 / 复杂 800…）
>   看起来像「中后台通用规律」，其实是某一个系统的设计决策。预置进去，
>   使用者会照着改而不是去采集——所以引擎那份是空的，
>   `--type` 按 `templates/` 下的目录名发现，`--overlay` 在契约为空时**拒绝执行并打印裁决步骤**

建包后顺序不能乱：

0. **先定交付路线**（v1.21 新增）：目标系统用 CSS-in-JS 组件库（antd 5 等）时，
   **双路线是必选项**——手写 HTML 到不了「与线上一模一样」，要加 `codegen/`
   （权威文件表 / 页面骨架 / 主题规则 / 硬性禁令 + 目标仓库内验证示例页），
   HTML 模板降级为结构走查稿。构成与验收见 `references/03-generation.md` §13。
   传统全局 CSS 系统跳过此步，单走 HTML 路线。
1. **先写 `foundation/tokens.md`**（裁决结果落地）
2. **再回灌各模板 `:root`** —— 反向操作必然双源漂移；
   `[E5] 取值待填` 归零才算回灌完成（模板里还留着 `unset` 时它会报数，这是预期的）
3. **沉淀 `scripts/layout/`** —— 按挖掘报告第 2 节的布局候选，逐套搭外壳；
   保留 `<!-- @content-slot -->`（必填）与 `<!-- @tabs-slot -->` / `<!-- @page-title -->`（选填）
4. **裁决 `scripts/templates/contract.json`** —— 先定本系统有哪几类页面（`types`，可留空按目录发现），
   再定浮层契约（有哪几类、每类几档、每档多宽、遮罩类名、`needles`）；
   流程见产出包 `scripts/templates/README.md`「怎么裁决本系统的契约」
5. **沉淀 `scripts/templates/<类别>/`** —— 按挖掘报告第 1 节的页面结构特征，
   只沉淀本系统确实有的类别；起手用 `scripts/templates/_skeleton.html`，
   类名与档位要和第 4 步的契约对齐
6. **裁决 `foundation/conventions.json`** —— 本系统的结构级约定写进去，`[E4]` 逐条校验；
   凡是「批量脚本可能漏掉某个文件」的约定都该写，靠肉眼审必然漏
7. **补 `components/` `pages/` 文档** —— 只写实际存在的类型，骨架见 `assets/doc-skeletons/`
8. **生成 `examples/` 标杆页** —— 用 `new-page.js` 出骨架再填真实业务文案
9. **更新包内 `SKILL.md`** —— 文档路由、强约束清单与维护规则（§1.2「判四件事」的
   答案来源、§7 的改动清单按本包实际沉淀回填；骨架自带收编三步与破例留痕的流程，不预置具体条目）

页面/组件类型、强约束清单、浮层档位都从本次采集与评审的结果里长出来，
**不抄其它系统的清单**——抄来的约束在本系统没验证过，等于没有。
同理，`foundation/conventions.json` 也不要照抄工厂包里的样例
（`assets/samples/conventions.sample.json` 只是样例，类名与结构假设只对那一套系统成立），
`templates/contract.json` 更不要照抄工厂包里的 `assets/samples/contract.sample.json`。

> **裁决改了值，引用不会自己跟上（破坏性更正的同步债）。** 档位收敛、语义取值改判、
> 归并关系变更（STARS 实测：弹窗 15 个实测值收敛 6 档，720→680、1600→fluid）落地时必须
> **全库 grep 旧值**——文档、模板、示例、`codegen/` 四类文件逐处同步，或显式标注
> 「存量迁移项」；归并映射（旧值 → 新档）写进裁决记录。规范值与它的全部引用是一对，
> 只改一半就是「一对东西只搬了一半」的又一次翻版（见 `references/04-pitfalls.md` §3.19）。

## 6. 阶段五：校验

```bash
$NODE <新包>/scripts/check-tokens.js <工作区> --strict
```

退出码必须为 0。七项：E1 硬编码 / E2 取值漂移 / E3 未定义引用 / E4 框架约定 /
E5 取值待填 / W1 规范未收编 / I1 规范未落地。

- `[E4]` 的规则来自**本包的** `foundation/conventions.json`，不存在或为空则不校验，恒为 0
- `[E5]` 是建包后第一个要清零的项：模板 `:root` 还是 `unset` 就是还没回灌
- `[I1]` 是信息项（规范有、全库零使用），不阻断交付，但要判断是校验器盲区 / 缺模板 / 规范虚胖

用 git 的仓库再装门禁：

```bash
$NODE <新包>/scripts/install-hooks.js install
```

## 7. 不可违反

1. **数值必须有出处**：设计稿 / 线上实测 / 人工确认，三者居一。禁止「看着合理」就写
2. **先规范后回灌**：改 Token 一律先改 `tokens.md`，再回灌模板 `:root`
3. **语义命名不由机器裁决**：挖掘结果只是频次排序
4. **双向校验不算多余**：只查「交付物按没按规范写」，会漏掉「规范没收编」的私有 Token
5. **不生搬硬套**：
   - 布局外壳按**本系统的设计稿/线上实测**搭，不从别的系统抄
   - **内容区模板同理**——它不只是结构，还带着一整套取值阶梯；抄过来等于把别人的
     间距档 / 色板 / 圆角档固化成本系统的规范条目
   - **契约取值同理**——「有哪几类页面、浮层分几档、每档多宽」是设计决策，
     不是「中后台通用规律」。`contract.json` 建包时是空的，要按设计稿裁决
   - **骨架里预设的条目同理**——`tokens.md` 的待确认清单、`SKILL.md` 的强约束清单、
     引擎 README 的验收清单，都不预置条目：清单要指向**本系统的采集结果**
     （挖掘报告 §8 存疑项 / 人工标注 `openQuestions`），不是替使用者想好的答案
   - 强约束 / 组件清单 / 框架约定都从本系统实际特性生成
   - 迁移已有实现时用 `--seed-templates`，取值默认中性化为 `unset`，逼人回灌
6. **脚本类能力必须实测**：建包器、采集器、生成器改完要在临时目录真跑一遍，
   纸面推演查不出 `ROOT` 引用在前赋值在后这类 bug
7. **文档承诺的能力代码必须做得到**：写进 SKILL.md 的命令逐条跑过再交付
8. **改完工厂必须自检**：见 §8。工厂自身没有校验，前七条就只是倡议
9. **产物必须可移植**：生成器与引擎**不得把绝对路径写进产物**。
   - 文档骨架写「本包所在目录（即本文件 `SKILL.md` 的上一级）」，不写 `/Users/…`；
   - 包内脚本一律 `path.join(__dirname, '..')` 自定位，不依赖调用者的当前目录；
   - 交付前扫一遍：`grep -rl "/Users/\|C:\\\\" <包目录>`。
     剩下的应该只有**出处记录**（「这个值采自哪个仓库」）——那是合法的历史事实。
   - **最终验收要在交付副本上跑**，最好再解压到临时目录跑一遍：
     「源目录能跑」不等于「拷出去能跑」。
   > ⚠ 写死绝对路径的后果**不是「别人跑不了」**（那还算好的，至少会报错），
   > 而是**「跑的是另一份包」**——若那个路径上恰好还有一份旧副本，
   > 校验器会打印「全部通过」，而它看的是旧那份。**假通过比报错难查。**
   > `[S26]` 守着这条。
10. **代码路线的交付物必须过目标仓库的工具链**：tsc / lint 零错误 + 裸色值扫描 +
    路由注册说明，缺一不算交付。依赖装不上时把「未验证」显式写进交付说明——
    留白会被读成「已验证」（「写了」不等于「交付了」，见 `04-pitfalls.md` §3.19）。

## 8. 改完工厂必须自检

这个工厂最常出的问题不是单点 bug，而是**工厂自己没人校验**：工作区与安装副本
悄悄分叉（而实际运行的是安装副本）、文档登记了不存在的模板、上游系统的产物漏进
「通用引擎」、版本号各写各的。这些都纸面看不出来，跑一遍才知道。

```bash
$NODE $FACTORY/scripts/self-check.js          # 退出码必须 0
$NODE $FACTORY/scripts/self-check.js --quiet  # 只打失败项
```

27 项检查：JS 语法 / 引擎登记表双向一致 / 取值纪律（`:root` 外无色值 +
同名 Token 取值唯一，覆盖引擎骨架与样例）/ 引擎不预置布局、内容区模板与契约取值
（`contract.json` 必须是空契约，填了取值就报错）/ 引擎文档不越界 / 骨架占位符都有来源 /
版本号一致且有变更记录 / 样例已标注 / 工作区↔安装副本逐文件一致 / 陈旧副本提示 /
模板契约（生成器 `@@占位符@@` ↔ 骨架说明）/ 样例模板都有「业务替换点」标记 /
演示区标记（`@transient` 成对 + `data-collect-ignore`）/ 引擎骨架不带具体系统的设计锚点 /
**CSS 切分健壮性**（注释与字符串里的花括号不得带偏 `splitRules` / `scopeCss`）/
**约定匹配边界**（`contains` 的选择器边界不得漏掉 `-` / `--`，BEM 假阳性）/
**采集口径**（采集器「不可见节点」判定的正反样例——判错会整体污染采样，
出来是一份「看起来正常」的错误报告，见 `CHANGELOG.md` v1.9）/
**注释字面量**（HTML 注释里的标签字面量不得带偏 `parts()`，会吞掉后半份模板）/
**约定类型**（`[E4]` 的规则类型：文档承诺的与校验器实现的双向一致）/
**系统名不硬编码**（生成器不得给某个系统的名字兜底，会静默贴错品牌文案）/
**结构计数口径**（采集器不得把 `<svg>` 图标算成图表，会凭空推断出仪表盘页，见 v1.14）/
**双主题口径**（主题覆盖块算「定义」、亮色列靠格式自证、相邻块不漏、注释不越界，见 v1.15）/
**自检项数量**（本节登记的「N 项检查」必须与实际项数一致——它曾长期停在 17 而实际已有 21）/
**生成器并亮色块**（`:root` 与亮色覆盖必须成对搬——只搬 `:root`，亮色下一半元素静默沿用暗色，
而生成器输出的逐项计数全是 0，真因是 `[E6]` 没被打印出来，见 v1.15）/
**介绍网页同步**（`介绍-设计系统工厂.html` 是全厂唯一一份**手工维护**的产物，
版本 / 自检项数 / 更新日期 / 校验码集合四项必须与工厂一致——它曾停在 v1.0 而工厂已到 v1.15，见 v1.16）/
**建包产物可移植**（生成器不得把绝对路径注进文档骨架——产物拷给别人后，
若那个路径上恰好还有一份旧副本，包内脚本会去校验**旧那份**并打印「全部通过」，见 v1.17）/
**骨架校验口径**（`PACKAGE-SKILL.md.tpl` §3 复述的校验码集合与项数必须等于引擎真做的——
引擎加了 `[E6]`、骨架也改了，而**按旧骨架生成的那个包**一路带着「七项检查」进了交付 zip；
`[S23]` / `[S25]` / `[S26]` 三处都不覆盖它，见 v1.18）。

> **检查项要跟着它管的东西搬家，也要跟着新出现的失败模式增长。**
> 每加一条都要做**负向测试**——改回旧实现，确认它真的会红。
> 只会变绿的检查等于没有检查。
>
> `[S15]` / `[S16]` / `[S22]` 是同一类：**给引擎自己的判断加断言**。
> 前者管「解析器把合法输入读错」，`[S16]` 管「匹配器把合法选择器判错」，
> `[S22]` 管「定义块的口径把合法交付物判错」。
> 这类缺陷不报错、也不漏报，而是**报错报错了地方**（假阳性），
> 会让人去改本来正确的东西。凡是引擎替使用者做判断的地方，都要问：边界我测过吗？
>
> `[S24]` 是另一类：**「一对东西只搬了一半」**。`[S24]` 管 `:root` 与亮色覆盖，
> 同族的还有「契约与骨架」「文档与实现」「清单与文件」。判据都是同一个：
> 加了 A 之后，**与 A 成对的那个 B 有没有跟着走**。
>
> ⚠ **「检查报红」的第一反应不应该是改交付物。** 判据是：
> **把交付物改成「不按规范写」之后报错消失了吗？** 消失了，说明校验器在惩罚规范，
> 该改的是校验器（见 `references/04-pitfalls.md` §3.13）。
>
> ⚠ **自检全绿 ≠ 产物正确。** `self-check.js` 只管工厂，`check-tokens.js` 只管取值与结构约定，
> 两者都**看不见几何**。交付前还要跑一遍真实浏览器几何回归，见 §7。

**失败时的标准动作**：先在工作区改到全绿 → 跑端到端实测 → 同步安装副本 → 再跑一次自检。

```bash
rsync -a --delete --exclude='.workbuddy-ai' --exclude='.DS_Store' \
  $FACTORY/ ~/.workbuddy-ai/skills/design-system-factory/
```

> `[S10]` 只**提示**已知的旧分支副本，不自动删——删别人的目录不是自检该干的事。

**改工厂的同时要改 `CHANGELOG.md`**，并让三处版本号一致
（`SKILL.md` / `README.md` / `CHANGELOG.md`），否则 `[S7]` 会拦下。
