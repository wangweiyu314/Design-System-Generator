01它是什么，为什么需要它

一句话：把「建一套设计系统」变成有流程、有校验、可复现的工程——产出的是机器可执行的约束，不是给人看的文档。

设计规范的真正用途，是约束那个写代码的角色。现在这个角色越来越多是 AI——但它读不进几十页文档，也记不住口头约定，于是颜色自己编、间距自己凑。

更麻烦的是这类错误不报错：CSS 能跑、页面能看，硬编码色值和数值漂移混在几百行 diff 里，只能靠 review 一句句挑——这是 AI 生成代码之后最现实的质量瓶颈。

规范读不进，也读不全
几十页规范塞不进上下文，Agent 只看得到片段，剩下的颜色间距全靠它自己猜。
写错了没人发现
硬编码、数值漂移混在几百行 diff 里。CSS 不报错、页面能跑，人眼抓不住。
没有门禁，全靠自觉
prompt 里写了「必须遵守规范」，Agent 转头就忘，没有任何机制真的拦得住它。
× 过去
规范停在文档里 → Agent 读不全，颜色自编、间距自凑 → 没有校验环节，只能靠 review 人眼抓。
✓ 现在
数值落成 Token 单一真值源 → 校验器双向比对 → 提交门禁让约束自动生效，不合规卡在 commit。
立场一：每个数值都要有出处。 出处只有三种——设计稿（意图）、线上实测（现状）、人工确认（裁决）。 拿不到设计稿时，前端源码是第三类权威：它既不是意图也不是现状，而是现状的成因，而且带着框架的语义名——频次排序永远推不出「这个红是错误色还是品牌色」，源码一眼就能看出来（见 §05）。
立场二：不生搬硬套。 布局外壳、内容区模板、强约束清单、浮层档位，全部由本系统的实际采集结果生成，不复制任何既有系统的数值与规则。抄来的约束在新系统没验证过，等于没有（见 §02 第 4 步与 FAQ）。

02十分钟走一遍：从零到一套技能包

以下是一个完整教程。假设你要给「某某资管平台」建规范包，每一步给出：做什么、敲什么、会看到什么、谁来拍板。命令可复制，路径按实际环境调整。

0
备料：三种输入，能拿几样拿几样人
输入怎么拿产出什么
设计稿（意图）Figma MCP 接入，或让设计师导出 Tokens Studio / Variables JSON·CSV，实在不行用截图人工标注设计意图值，用于与线上实现双向核对
线上页面（现状）Agent 能直连就自动采；内网需登录时，把采集脚本发给能打开页面的同事在控制台粘贴运行*-styles.json：真实渲染取值与结构特征
前端源码（成因）
拿不到设计稿时的主要腿		组件库仓库或打包产物 dist/*.js所有主题分支取值 + 框架语义名 + 路由条件分支表
两条备料纪律。 ① 线上采集至少 3 个不同页面（列表 / 表单 / 详情各一），单页噪声极大；状态色（hover / active / disabled）默认态采不到，要在页面上手动触发后再采一次。 ② 开工前先找历史采集与旧规范包——有就做差异合并而不是重做；团队已有的规范文档只索引不复制，另建逐条映射。
1
采集AI
# 设计稿侧：走 Figma MCP / REST 读节点树，
# 产出与线上采集同构的 JSON；--evidence 那份机器证据要先读，它是第 3 步裁决的输入
$NODE $FACTORY/scripts/collect-from-figma.js --key=<fileKey> \
  --token-file=<token文件> --out=<采集目录> --evidence=证据.md

# 线上侧（内网/需登录时）：不要硬闯。把脚本发给能打开页面的人，
# 在登录后的控制台粘贴运行——只读 DOM，不发请求、不改页面、不碰登录态

能直连的线上页面则由 Agent 用 CDP 接管一个已登录浏览器，多页采集、浮层状态、截图全部自动化，不用人工粘贴。

2
挖掘：多页合并统计AI
# 至少三页采集 + 设计稿导出一起喂进去
$NODE $FACTORY/scripts/mine-tokens.js \
  --online=list-styles.json,form-styles.json,detail-styles.json \
  --figma=figma-vars.json \
  --out=mining-report.md --emit-tokens=tokens.draft.md

会得到两份产物。mining-report.md 八节：

  • §1 页面结构特征——推断该建哪些页面文档（不建不存在的东西）
  • §2 布局候选——按几何指纹聚类出几套页面外壳（第 4 步沉淀布局的唯一依据）
  • §3–§6 颜色 / 字阶 / 间距与网格 / 圆角阴影——按频次排序的候选
  • §7 设计稿↔线上差异（F1 设计稿有线上无 / F2 线上有设计稿无）
  • §8 存疑项（必读）——机器判不了、必须人工确认的问题

tokens.draft.md 是 Token 候选表， Token 名还是 --color-candidate-N 这类占位名。

注意：频次排序不等于语义。 「#2A6CDD 出现了 47 次」是机器算的；「这是品牌主色」必须人说了算。挖掘器只给候选和存疑，不做命名裁决。
3
裁决：语义命名与意图源人 · 不可跳过

把 mining-report.md 与 tokens.draft.md 摆给用户 / 设计师逐项确认。这一步不能跳过、不能由 AI 代劳——语义命名猜错的代价远大于猜对的收益，一个错的主色会顺着模板扩散到几十个页面。

确认清单不预置条目，从两处长出来：挖掘报告 §8「存疑项」、采集评审中挂起的问题。另有几项固定要裁：

  • F1/F2 差异：哪边是意图源（设计稿超前，还是线上遗留）
  • 网格基数：4px 还是 8px；不合网格的间距是设计不规整还是基线不同
  • 页面类别 / 布局候选：本系统实际有哪几类页面、几种外壳
  • 浮层契约：有哪几类浮层、每类几档、每档多宽、遮罩类名

两种被实测证明可行的变体：条目多时可以分若干组批量问（结论表配「结论 + 落地位置」两列，靠落地位置清单防漏回填）；证据为「多个页面独立实现、取值逐字节一致」的项，AI 可先行收编但必须标注「可复议」并列出证据。

4
建包AI
# 系统名 + 类名前缀；带 --from-mining 可用草稿预填 tokens.md（候选值，仍需确认）
$NODE $FACTORY/scripts/init-package.js \
  --name=某某资管平台 --prefix=am \
  --from-mining=tokens.draft.md \
  --out=./am-design-specs

建包器复制引擎、全量替换 CSS 类名前缀（gf- → am-）、系统名与环境变量名，并生成规范文档骨架。产出的包长这样：

am-design-specs/ ├── SKILL.md 包内入口（判四件事 / 文档路由 / 强约束 / 维护规则） ├── USER-SKILL.md 用户级入口（可选装到技能目录，任意工作区唤起） ├── foundation/ │ ├── tokens.md 取值唯一来源（Token 名已预填，取值待填） │ ├── design-sync.md 设计稿 ↔ 规范映射与同步流程 │ └── conventions.json 本系统的结构级约定（[E4] 逐条校验） ├── components/ 只写实际存在的组件 ├── pages/ 只写实际存在的页面类型 ├── examples/ 标杆页 └── scripts/ ├── check-tokens.js Token 双向校验 + 框架约定回归 ├── check-design-sync.js 设计稿 ↔ 规范核对（抓两个真值源的偏差） ├── new-page.js 一键页面生成器 ├── install-hooks.js 提交门禁（不合规不让提交） ├── layout/ 本系统的页面外壳（建包时只有契约骨架） └── templates/ 本系统的内容区模板（建包时只有契约骨架） ├── contract.json 浮层遮罩类名 / 宽度档位 / --type 清单 └── <类别>/<名字>.html 目录名即 --type 取值
引擎刻意不预置三样东西。 ① 布局外壳——抄一套别家的外壳，它看起来能跑，直到有人发现侧栏宽度、面包屑位置、多标签行为全都不对，而那时它已被复制进几十个页面； ② 内容区模板——「表格就是表格」只对了一半：模板还带着一整套取值阶梯（间距档 / 色板 / 圆角档），抄过来规范里就凭空多出几十个看起来很像正经条目的 Token，而校验器是绿的，因为每条都被「登记」了； ③ 契约取值——「弹窗分几档、每档多宽」是设计决策，不是通用规律，预置进去使用者就会照着改而不是去采集。外壳与模板都要按第 2 步挖掘报告的 §2 / §1 逐套沉淀。
5
定稿回灌：先规范，后模板人 + AI

裁决结果落进 foundation/tokens.md（占位名逐个转正为语义名），再回灌各模板的 :root——顺序反了必然双源漂移。校验器的「取值待填」归零，才算回灌完成。

第 5 步没有捷径。 候选值必须经设计师确认才能定稿。占位名进了规范，等于给全库埋一颗叫 candidate 的雷。
6
校验、出标杆页、装门禁AI
# ① 校验：扫描根是包本身（不是它的上一级），退出码必须是 0
$NODE am-design-specs/scripts/check-tokens.js am-design-specs --strict

# ② 出标杆页：按本系统沉淀的类别生成骨架，再填真实业务文案
$NODE am-design-specs/scripts/new-page.js --type=list --name=产品列表

# ③ 有 git 的仓库装提交门禁：不合规的代码提交不了
$NODE am-design-specs/scripts/install-hooks.js install
到这里，一套技能包就交付了。 之后它是一个自持的系统：生成页面、双向校验、提交拦截都由包内脚本闭环（日常用法见 §03）。

03建好之后，日常怎么用

技能包的日常使用者也是 AI（或照着 SKILL.md 干活的人）：给一份 PRD，出合规页面。人只在两种情况下被需要。

拿到需求，先判四件事

判什么答案来源（都在包内）
判页面类型scripts/templates/ 下已沉淀的类别（目录名即 --type 取值）+ pages/ 结构规范
判布局0→1 的新系统出完整外壳；已有项目里加页面用 --layout=none 只出内容区，外壳沿用现有，不另起一套
判内容区模板scripts/README.md 选型决策树；模板复制改造，不手工拼装
判浮层档位contract.json 的 overlay；宽度只能取档位 Token，不允许自由写

判完走 new-page.js 生成骨架，按「业务替换点」注释逐项替换业务字段与数据。颜色、间距、结构一律引用 Token，不自己定值；生成后自跑校验，报错就改，改到零报错为止。

只有两种情况需要人拍板

一 · 规范没覆盖这个场景
先依据基础规范把页面搭起来，与使用者确认后补进规范，而不是绕开。收编三步：页面里先试出来 → 写回规范（先 tokens.md 再回灌模板）→ 全站把临时写法换成正式 Token。补一次，后续同类页面都受益。
二 · 业务上确实要破例
由人拍板并留下记录（写清场景与理由），不默默绕开校验；同时把类似场景整理出来——收编成正式档位或写进强约束。破例可以，但要能被查出来。
人不再逐页检查，只做两件事：定规则、判例外。 规范覆盖不到的地方由人补进规范，业务确实要破例的地方由人拍板并留痕——其余整条链路（读规范、选模板、生成、校验、提交）都可自动走完。
真实项目里换品牌色，改的是一行。 在 foundation/tokens.md 里改掉 --color-primary，回灌各模板 :root，跑一遍校验——所有引用它的组件与页面自动跟随，不会漏掉某个文件里的第 4 处抄写。

04八道校验，三道链路

规范写在文档里是死的，落进流程才有约束力。校验器逐行扫规范包，报错带文件名和行号。

检查项查的是
E1 硬编码正文出现、又没在 :root 声明过的色值字面量，逐行报出行号
E2 取值漂移文件 :root 的取值与 foundation/tokens.md 不一致——模板抄错了规范
E3 未定义引用写了 var(--x) 但本文件没定义，样式静默失效
E4 框架约定本系统的结构级约定回归，规则来自 conventions.json——校验器不认识任何具体系统的类名。凡是「批量改模板可能漏掉某个文件」的约定都写进来，靠肉眼审必然漏
E5 取值待填:root 里取值还是 unset——迁移模板时取值会被中性化，逼人回灌；回灌定稿取值后归零
E6 亮色覆盖不全声明了亮色覆盖块，却没覆盖全「亮色值 ≠ 暗色值」的 Token——这些 Token 在亮色下会静默沿用暗色取值，逐项计数全是 0 也要查它
W1 规范未收编交付物在定义和使用、规范里却没有的私有 Token（交付物 → 规范方向）
I1 规范未落地规范定义了但全库零使用——要么用起来，要么删掉，规范不攒废值
只做单向校验不算数。 只查「交付物有没有按规范写」，会漏掉「规范没收编」的私有 Token——这类 Token 曾悄悄长到 58 个才被发现：模板里在用、规范里没有，谁也不知道该听谁的。双向校验保证规范里写的就是全站实际在用的那套值，不是一份会过期的说明书。

三道链路，各管一段

生成时 · new-page.js
按页面类型自动拼装布局、内容区、多标签与浮层骨架，合并 :root 变量，写盘后立刻跑一次校验——骨架阶段就不带病。
提交时 · install-hooks.js
把校验装进 git pre-commit，不合规的代码提交不了。「这次先不跑」这个选项不存在，约束不依赖任何人记得。幂等、可卸载、可与既有 hook 共存。
设计稿变更时 · check-design-sync.js
比对设计稿导出与 tokens.md 两个真值源：抓同名不同值、设计稿有规范无、规范有设计稿无——人工转录误差不会悄悄变成规范。
「检查报红」的第一反应不是改交付物。 判据：把交付物改成「不按规范写」之后报错消失了吗？消失了，说明校验器在惩罚规范——该改的是校验器。假阳性会把正确写法拦住、逼使用者绕开规范，比漏检更糟。

专题一 · 没有设计稿：把前端源码当第三类权威

线上实测（computed style）只采得到「当前渲染出来的那一个值」，而且采不到「这个值叫什么」。源码补的正是这两个洞：

线上实测的盲区源码怎么补
只有「当前渲染的那一个值」源码里所有主题分支都写着，一次拿全
采不到「这个值叫什么」主题配置的键就是框架语义名（colorError / defaultBg）
只打开一页 → 以为全站一个底色路由条件分支函数能整张表抄下来
图表配色采不到（画在 <canvas> 上）源码里是明文的色值数组 + 分配函数

源码按权威度降序分四层：src/**/themes/*.json（语义名即权威，先扫这里）→ src/global.less → 打包产物内联的 JSON.parse('{…}')（只有 dist 时反解这里）→ 组件源码字面量。六个实测踩过的陷阱，最重要的三条：

  • 别假设有 darkAlgorithm——读实现再下结论；没有算法时，没被主题覆盖的 Token 两主题原生同值，没包进 Provider 的组件不响应切换。
  • 一对东西不能只搬一半——:root 与另一主题的覆盖块是一对，只搬 :root，另一半元素在亮色下静默沿用暗色。
  • 注释与代码矛盾、同一语义多套实现——以代码为准并记进待确认；多套实现全部列出标「两套」，不自动选一个。采不到的东西（<canvas>）显式写「能力边界，不是漏采」；浏览器验证取值前先关 transition，否则读到补间中间色。

源码取值的出处归属：主题配置是实现不是意图 → 记「线上实测（源码）」；用户看过点头 → 升格「人工确认」；与设计稿冲突 → 记待确认，不自动选。

专题二 · 包要能整体拷走

「跑得通」不等于「交得出去」。交付环节暴露的问题有个共同点：输出一切正常。最坏的一种是写死绝对路径——包内脚本指向一个恰好还存在的旧副本，校验器打印「全部通过」，它看的却是旧那份。假通过比报错难查，因为输出里没有任何异常信号。三条纪律：

  • 包内脚本一律「相对自身」定位，不依赖调用者的当前目录；
  • 交付前扫 grep -rl "/Users/\|C:\\" <包目录>，剩下的应该只有出处记录（合法的历史事实）；
  • 最终验收要在交付副本上跑，最好再解压到临时目录跑一遍。工厂自检的 [S26] 会真跑一次建包、逐文件确认产物里没有绝对路径。

专题三 · 什么时候该写代码，而不是更像的 HTML

手写 HTML 走查稿有天花板：目标系统用 CSS-in-JS 组件库（antd 5 等）时，交互态、图标、字体渲染、动效、滚动条都无法静态复刻——走查稿只能「接近」，永远不能「一致」，而「接近」在交付语境里是持续产生返工的承诺。判据只看一件事：目标系统的样式是不是运行时生成的。

目标系统样式技术栈路线
全局 CSS / Less / CSS 自定义属性单路线（HTML）——静态 HTML 能忠实复刻渲染结果
CSS-in-JS 组件库（antd 5 等）双路线：代码为主、HTML 降级为结构走查稿——包内新增 codegen/（权威文件表 / 页面骨架 / 主题规则 / 硬性禁令）
「写了」不等于「交付了」。 代码路线的验收闭环缺一不算交付：tsc 零错误 + lint 零错误 + 裸色值扫描 + 路由注册说明；依赖装不上时把「未验证」显式写进交付说明——留白会被读成「已验证」。
建好之后的同步债。 裁决改了值，引用不会自己跟上：档位收敛、语义改判后要全库 grep 旧值，文档 / 模板 / 示例 / codegen 四类文件逐处同步或标注「存量迁移项」，归并映射写进裁决记录。语义色值还可能被后来的挖掘推翻——「全库只此一处」的结论必须记录搜索范围，新增标杆页挖掘后要复核既有语义结论。

06它不做什么

边界说清楚，比吹能力有用。

不裁决语义命名
主色、成功、警告、错误这些语义必须有设计师确认。脚本只给频次排序。
不代劳登录态
内网页面不去硬闯。改由能打开页面的人跑采集脚本，交回 JSON。
不生成业务文案
标杆页只出骨架与规范样式，业务字段、数据、提交逻辑要逐项替换。
不预设页面类型
结构特征信号为 0 的页面类型不建文档，避免照着做出一个系统里根本没有的页面。

07常见问题

多数来自真实建包过程中被问过、踩过的问题。

问答
一定要有 Figma 吗？不一定。但只有线上采集时，规范描述的是「现状」而非「意图」，历史遗留脏值会被洗白成标准。拿不到设计稿就走源码这条腿（§05 专题一）。
线上页面一个都打不开？走人工标注：截图 + 填 examples/intake.sample.json。质量下降，但比硬编数值强。
能直接复制现成规范改改吗？不能也不该。取值、约束、布局外壳、内容区模板都是特定系统的产物，在你这套里没验证过，等于没有。所以引擎只给契约骨架（§02 第 4 步）。
内容区模板也要自己搭？「表格就是表格」不是吗？只对了一半。结构确实大体相似，但模板还带着一整套取值阶梯——间距档、色板、圆角档，那些是上一套系统的设计决策。抄过来的后果是这些 Token 名被登记进 tokens.md，每条看起来都像正经规范项，而校验器是绿的。
前端源码和线上实测冲突，听谁的？都先别信。把冲突记进待确认清单，交给用户裁决——冲突往往意味着「线上跑的是旧版本」或「有多个入口改了同一处」。自动选一个等于替用户做了他没授权的决定。
一套规范该写几个主题？有几个写几个，但别只写主视角那一个。另一个主题的取值要么在源码里有、要么就是一条待确认项，不是可以留空的格子——留空的下场是交付物在另一个主题下静默沿用当前主题取值。
校验通过就完事了？退出码 0 只是及格线。规范要跟着设计稿升级持续维护：产出包里 foundation/design-sync.md 定义同步流程，check-design-sync.js 定期比对两个真值源。
裁决把档位 / 取值改了之后呢？全库 grep 旧值，四类文件逐处同步或标注「存量迁移项」，归并映射写进裁决记录。实测教训：弹窗宽度从 15 个实测值收敛 6 档时，720→680、1600→fluid 两处破坏性更正的引用同步全靠手工——「规范值」与「它的全部引用」是一对，只改一半就是双源漂移。
包自己跑通了，就能发给别人了吗？不一定，失败方式很隐蔽：最坏是写死绝对路径后校验「旧副本」假通过（§05 专题二）。交付前在交付副本上再跑一遍验收。
什么时候需要双路线（代码 + HTML）？判据只看一件事：目标系统的样式是不是运行时生成的。CSS-in-JS 组件库是——此时代码路线是必选项，HTML 降级为结构走查稿；传统全局 CSS 系统单走 HTML 仍然成立。
代码路线的交付怎么算「完成」？四项闭环缺一不算：tsc 零错误、lint 零错误、裸色值扫描干净、路由注册与权限配置说明。依赖装不上时，「未验证」要显式写进交付说明。
校验器会不会把正确写法判错？会，而且这比漏检更糟——假阳性会逼使用者绕开规范。判据：把交付物改成「不按规范写」，报错消失了吗？消失了，该改的是校验器。另外，一次就绿的检查必须反向验证（改回旧实现确认它真的会红），只会变绿的检查等于没有检查。
